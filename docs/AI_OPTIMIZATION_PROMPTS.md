# AI 优化提问指南 —— 怎么让 AI 给出可落地的建议

> 经验来源：v0.2 外部评审中约 1/3 建议不适用（fcntl 在 Windows 不存在、
> 误判"缺断网缓冲"、Prometheus/多进程过度设计）。
> 本文档给出现成的提问模板，配合 [AI_REVIEW.md](AI_REVIEW.md) 使用。

---

## 一、三条核心原则（为什么上次会翻车）

| 教训 | 原因 | 对策 |
|------|------|------|
| 建议无法落地 | AI 不知道平台约束 | 每次提问必附"约束清单" |
| 建议重复已做的事 | AI 没跑代码 | 附 AI_REVIEW.md 已拒绝项 + 让它逐条验证 |
| 方案过度设计 | AI 默认企业级场景 | 明确"个人项目、单进程、零运维"定位 |

## 二、提问模板库（直接复制，替换【】内容）

### 模板 1：全项目优化评审（通用）

```
你是资深 Python 工程师。请分析附件项目（个人智能助手：Windows 采集器 +
FastAPI 服务端 + PySide6 悬浮球，实现记忆/分析/学习闭环），找出可优化点。

【硬性约束】
- 服务端单进程 ASGI，不引入 Redis/Docker/K8s/Prometheus 等企业设施
- 采集器运行在 Windows（Python 3.10+），所有建议必须 Windows 可用
- 个人项目，单人维护，复杂度换收益比是首要标准
- 隐私敏感：浏览器历史等行为数据只做聚合，不上传原文

【已定设计，不要推翻】
- SQLite + sqlite-vec 存储（WAL 已开）
- 记忆评分 = 相似度 × importance × 时间衰减 × topic boost
- 断网落盘重试、心跳上报已实现

【输出格式】
1. 结论表：问题 | 严重度(P0/P1/P2) | 具体文件:行号 | 改法
2. 每个建议必须标注"验证方式"（怎么确认它真的成立）
3. 你认为不需要改的，写明不适用理由

请先读 docs/REFERENCES.md 理解设计意图，再读 docs/AI_REVIEW.md 避免重复已拒绝项。
```

### 模板 2：单模块深挖（以记忆系统为例）

```
只分析附件中的记忆系统（server/app/core/memory.py、models/database.py、
services/consolidation.py）。其他模块不要提。

【当前实现】（贴代码或指出文件）
【问题】
- 检索评分公式有什么缺陷？遗漏了什么信号？
- 摘要整合的 prompt 有哪些边界情况会输出坏 JSON？
- 单表 memories 设计在 10 万条时哪些查询会变慢？给具体 SQL 分析
【约束】不引入外部向量库；改动必须兼容现有 SQLite schema（或给迁移方案）
【输出】按优先级排序的具体修改建议，每条附修改位置和前后代码对比
```

### 模板 3：基于上次评审迭代（防止重复）

```
这是上一轮 AI 评审的筛选记录（docs/AI_REVIEW.md），其中已采纳 6 项、拒绝 9 项、
进入路线图 4 项。请基于当前最新代码（v0.2+）：
1. 验证已采纳项是否实现正确、有无引入新问题
2. 路线图 4 项（多粒度摘要/聚类去重/知识图谱/精细监控）按"个人项目收益"重新排序，
   给出每项的启动条件（什么信号出现才值得做）
3. 找"上一轮没发现"的新问题——重点看并发、异常路径、边界输入
不要重复已拒绝的 9 项，除非有新的证据。
```

### 模板 4：要代码不要建议（落地模式）

```
针对【具体问题】，直接给出可运行代码：
- 指明文件路径、修改前后完整 diff 风格对比
- Python 3.10+ / Windows 兼容
- 不改动现有 API 契约（除非说明原因）
- 附 2 条边界测试用例
输出后自查：这段代码在 Windows 上能跑吗？有没有引入新依赖？
```

### 模板 5：方案选型对比（拿不定主意时）

```
对【问题】，给出 2-3 个方案对比：
| 方案 | 复杂度 | 收益 | 风险 | 个人项目适合度 |
必须基于本项目的真实规模（预计一年内：记忆 <10 万条、日事件 <5000 条、
单用户）评估，而不是通用场景。最后给明确推荐 + 一句话理由。
```

## 三、必带材料（固定搭配）

1. **代码**：`PROJECT_BUNDLE.md`（`python scripts/build_ai_bundle.py` 生成）或 Release 里的 zip
2. **设计意图**：`docs/REFERENCES.md` —— 让 AI 知道"为什么这么设计"而不是"按惯例应该怎么设计"
3. **历史评审**：`docs/AI_REVIEW.md` —— 防止重复建议已拒绝项
4. **约束清单**：模板 1 里的【硬性约束】段，每次必附

## 四、追问技巧（第一轮回答不满意时）

| 场景 | 追问话术 |
|------|----------|
| 建议太泛 | "把你说的第 N 条写成具体代码，指出文件和方法名" |
| 没验证就下结论 | "你怎么确认这个问题真的存在？给出可在项目里执行的验证命令" |
| 想推翻已有设计 | "当前设计的原因见 REFERENCES.md 第 X 节，你的方案相比它多解决什么问题？" |
| 建议互相矛盾 | "第 2 条和第 5 条冲突，按个人项目标准选一个，说明理由" |
| 给的代码可疑 | "逐行解释这段代码，并指出在 Windows/Python 3.10 上的潜在问题" |

## 五、推荐工作流（三轮制）

```
第 1 轮：找问题（模板 1）      → 拿到问题清单
第 2 轮：筛方案（模板 3/5）    → 用 AI_REVIEW.md 标准筛选，标 P0/P1/P2
第 3 轮：写代码（模板 4）      → 要求可运行代码 + 测试用例
之后：人工（或让 AI）自查"Windows 能跑吗/引入新依赖吗"
```

关键纪律：**AI 的建议永远先过筛选再进代码**。v0.2 的流程（评估 → 采纳 6 项 /
拒 9 项 / 修 3 个连带 bug）就是标准示范：一次评审真正有价值的往往不是建议本身，
而是它逼你复查代码时暴露的真实问题。
