# AI 助手操作笔记本：四种架构选型分析

> 2026-08-27 研究记录。背景：个人 AI 助手（桌面机器人 + Windows 采集器 +
> 服务器 LLM）的执行通道选型。四种方案并非互斥，而是演进阶梯：
> **A 是底座，B 是管道升级，C 是接口标准化，D 是自治层。**

## 现状定位

当前系统是 **A（HTTP Local Agent）的顶配变体**：

- 云端队列：`executor_commands` 表 + 采集器 5s 轮询（幂等、断线排队、
  30min TTL 防僵尸指令）
- 桌面本地直行：聊天面板先本地解析执行（copy/backup/move/rename/
  list_dir/read_file/open/run_script），**执行类命令不经过服务器**——
  比标准 A 更"本地优先"，隐私更强
- 事件通道：采集器批量补推（HTTP），服务器幂等去重

## 四种方案对照

| 方案 | 通信 | 云端职责 | 本地职责 | 实现难度 | 实用性 | 备注 |
|---|---|---|---|---|---|---|
| A. HTTP Local Agent | HTTP 轮询 | 意图解析、指令入队 | 轮询执行、结果回传 | ⭐⭐ | ⭐⭐⭐⭐⭐ | 当前架构 |
| B. WebSocket 长连接 | 双向长连接 | 实时推指令/流式回复 | 实时推事件 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 体验升级，需 A 兜底 |
| C. MCP | 工具协议 | 模型按 schema 选工具 | MCP server 暴露工具 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 接口标准化，多前端复用 |
| D. 本地 Planner + 云端 Brain | 目标级 | 复杂推理 | 自主规划+执行 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 终局形态，需审批门 |

## 逐条结论

### A：最适合单用户内网的底座

- 队列 = 断线缓冲区 + 重试幂等的天然实现，排障成本最低
- 缺点（轮询延迟）已被"桌面本地直行"绕开
- QQ 远程通道接入时，服务器队列直接复用，零新架构

### B：体验升级，不是架构替换

- 收益：毫秒级推送、聊天流式回复、事件实时入库
- 代价：重连/心跳/握手鉴权/断线排队，每一项都是坑
- 原则：**A 兜底 + B 加速**，绝不用长连接替换队列

### C：接口标准化，边际收益在当前场景最小

- 正则路由的寿命与工具数量成反比；工具 >10 个或多前端时值得上
- 前置条件：验证 LLM 通道的 function calling 支持；工具选择开始烧 token
- 演进方式：执行器内核不变，外面包一层 MCP server

### D：终局，但必须半自主起步

- 目标级自治："把本周项目文件归档打包"（列目录→筛选→复制→打包→汇报）
- 硬约束：每步白名单校验 + 危险动作审批 + 执行日志回传（安全分级延伸）
- 本地小模型跑 Planner（OpenCode 桌面版可承担），断网可干活
- 起步姿势：Planner 只出计划 → 用户点头 → 逐步执行，别一步到位

## 推荐路线

1. **现在**：守住 A，做 QQ 接入（远程通道让 A 的价值闭环）
2. **体验**：SSE 流式回复 + 主动推送（SSE 比 WS 简单，够用）
3. **规模化**：执行器包 MCP 壳，工具注册制
4. **收官**：本地 Planner + 审批门，12 周项目亮点模块
