# LESSONS —— 实践日志与踩坑记录

> 记录项目从首次部署到运行的每个问题、根因与修复。
> 时间跨度：2026-08-23 ～ 08-26（六课带教 + 进阶课 9/10 + 十余次迭代）。
> 原则：**每个 bug 都配"根因 + 修复 + 教训"**，后来者（未来的自己）别重蹈覆辙。

## 一、部署与网络（第 1 课）

### 1.1 sqlite-vec 扩展加载失败（Linux）
- **现象**：启动日志 `sqlite-vec 不可用，向量检索已禁用: no such module: vec0`
- **根因**：`load_extension("vec0")` 按名字找扩展文件，Linux 上 SQLite 找不到
- **修复**：改用 `sqlite_vec.loadable_path()` 让包自己给出路径（v0.4）
- **教训**：扩展库要"问库本身要路径"，别手写名字

### 1.2 vec0 查询语法错误（隐藏最深的 bug）
- **现象**：本地测试全过，但真实环境向量检索静默不工作
- **根因**：vec0 是 **KNN 虚拟表**，不能当普通列 `WHERE v.distance < ?` 查询，
  必须 `WHERE v.embedding MATCH ? AND k = ?`；且默认 L2 距离与评分公式不匹配
- **修复**：改用 MATCH 语法 + 建表指定 `distance_metric=cosine`（距离 0~2，sim=1-distance）
- **教训**：测试环境没装扩展 → 一直走关键词兜底分支 → 掩盖了主路径 bug。
  **兜底逻辑必须定期验证"主路径真的能跑"**（后来补了 test_vector_search.py 端到端测试）

### 1.3 mount("/") 吞掉 API 路由
- **现象**：`/api/health` 404
- **根因**：Starlette 按注册顺序匹配，静态页 `mount("/")` 注册早于 health 路由
- **修复**：mount 移到所有 API 路由之后 + 注释警示
- **教训**：兜底型路由（mount /、404 handler）永远放最后

### 1.4 三层 API Key 排查（经典排障路径）
- **现象**：聊天接口连续 401
- **过程**：① DeepSeek 官方地址 + OpenCode key → "key invalid"
  ② 智谱地址 + DeepSeek key → "令牌已过期" ③ OpenCode Zen 地址 → "余额不足"
  ④ **OpenCode Go 地址**（`/zen/go/v1`）→ 成功
- **根因**：OpenCode 有两个网关（Zen 按量/Go 订阅），key 相同端点不同；
  且 DeepSeek 官方 key 与 OpenCode key 不通用
- **教训**：401 只是"拒了"，**错误信息里的每一处差异都是线索**（invalid ≠ 过期 ≠ 余额不足）

### 1.5 两层防火墙（云服务器经典坑）
- **现象**：本机 curl 通、公网不通
- **根因**：京东云安全组放行了，但系统 ufw 只放行 22
- **修复**：`ufw allow 8000/tcp`（后演进为 Tailscale 方案）
- **排障顺序（记住）**：① 本机 curl ② `ufw status` ③ 云安全组 ④ 确认 IP 对不对

### 1.6 误访问错误 IP 的 502
- **现象**：浏览器访问 `A.B.C.D:8000` 报 502
- **根因**：那根本不是本机 IP（502 来自别的机器上的服务）；正确 IP 另有其址
- **教训**：**排障第一步永远是"确认我在操作哪个对象"**

## 二、记忆系统（第 2 课）

### 2.1 facts 主语张冠李戴
- **现象**：摘要整合把用户消息里的"我"标成 subject="AI"
- **根因**：整合 prompt 缺"对话双方是谁"的上下文
- **修复**：prompt 明确"用户消息中的我/本人/咱们 → subject='用户'"
- **教训**：**结构化抽取的 prompt 必须交代语境**，否则模型默认站在自己的视角

### 2.2 中文时间解析正则（两个坑一次踩中）
- **现象**："下午3点到5点"解析不出 time_range
- **根因**：① 字符集写了"至"但口语说"到"（两个不同的字）
  ② "下午"没有 +12 小时逻辑 ③ 纯数字正则抢先匹配"2-5"
- **修复**：字符集补"到"、下午/晚上 +12、中文口语正则优先匹配 + 6 个回归测试
- **教训**：**正则对中文口语要穷举变体**；修复必配回归测试（test_worklog.py）

## 三、行为采集（第 3 课）

### 3.1 进程名全是 unknown（静默错误）
- **现象**：app_usage 事件 name=unknown，但窗口标题正常——**程序不崩，数据是错的**
- **根因**：ctypes 未声明 `restype`，64 位 HANDLE 被截断为 32 位；
  受保护进程（任务管理器）本来就禁止查询
- **修复**：全部 Win32 函数显式声明 restype/argtypes；失败降级为"标题猜名"
- **教训**：① ctypes 句柄必声明 c_void_p ② 静默错误比崩溃更危险——
  **验证要"看数据"而不是"看日志没报错"**

### 3.2 换目录导致事件重复推送
- **现象**：git clone 新目录后启动，一次补推 132 条历史，数据库 46% 重复
- **根因**：采集器游标（cursor）存在本地 cache/，换目录=记忆清零=按设计补推 24h 历史
- **修复**：服务器端**幂等**——按 (kind,name,detail,start_ts) 去重，重复只入库一次
- **教训**：**推送系统必须幂等**。采集端记忆会丢（换机/重装），服务端要能消化重复

### 3.3 心跳静默失败
- **现象**：服务器收不到心跳，但两边日志都"看起来正常"
- **根因**：`except Exception: pass`——失败无痕
- **修复**：成功/失败都打日志
- **教训**：**静默吞异常 = 排障黑洞**；兜底分支至少留一行日志

### 3.4 git 中文 commit 编码崩溃
- **现象**：git 扫描报 `'NoneType' object has no attribute 'strip'`
- **根因**：`subprocess.run(text=True)` 用系统 GBK 解码 git 的 UTF-8 中文输出 → 崩溃；
  且 `out.stdout` 未做空值防御
- **修复**：`encoding="utf-8", errors="replace"` + `(out.stdout or "")`
- **教训**：**Windows 上 subprocess 抓中文输出，text=True 是陷阱**——
  它用 locale 编码（GBK）解码 UTF-8 内容；显式 encoding 最稳

## 四、安全加固（第 3 课末尾）

### 4.1 公网裸奔的教训
- **风险**：8000 无鉴权时，任何人可 ① 白嫖 /api/chat 烧 LLM 额度
  ② 拉取 /api/stats 看行为数据 ③ 塞假事件污染统计
- **修复（四层防御）**：
  1. `API_TOKEN` 全局鉴权中间件（32 字节随机，白名单仅 / 与 /api/health）
  2. Tailscale 专线：公网 8000 从 ufw + 安全组双移除，只剩 SSH 22
  3. 隐私脱敏：敏感信息出网前本地正则替换
  4. 数据幂等 + 心跳（间接防污染）
- **教训**：**"能跑通"和"能安全跑"是两件事**；端口一旦暴露公网，先问
  "谁还能用我的钱包和日记"

## 五、桌面机器人（第 4 课）

### 5.1 拖拽失效（Qt 拖拽标准写法）
- **现象**：机器人无法拖动
- **根因**：松手瞬间用坐标差判断"点击 vs 拖拽"，窗口移动后计算不可靠；未显式 accept
- **修复**：拖动过程中位移 >3px 即标记 `_moved`，松手按标记决定；全事件显式 `event.accept()`
- **教训**：**状态在过程中记录，不在结束时反推**

### 5.2 无边框窗口"关不掉"
- **现象**：聊天面板无关闭按钮，Esc 无效，Ctrl+C 刷 Traceback
- **修复**：✕ 按钮 + Esc（需 `setFocusPolicy(StrongFocus)`）+ 机器人右键菜单退出 + SIGINT→app.quit()
- **教训**：**自定义窗口要自己补齐标准窗口的每一项能力**（关闭/焦点/退出）

### 5.3 交互误触（单击 vs 双击）
- **问题**：单击即弹面板，想"点一下看看状态"总是误开聊天框
- **方案**：双击开面板，单击只眨眼反馈（移动始终不弹）
- **教训**：**高频动作（移动/查看）不应绑定重操作（打开面板）**；交互分级：单击=反馈、双击=动作、拖拽=移动

### 5.4 内存审计（三个长期运行风险）
| 风险 | 修复 |
|---|---|
| QTextBrowser 聊天记录无限增长 | `setMaximumBlockCount(500)` 硬上限 |
| 5 处 QThread 未 deleteLater 慢性泄漏 | 统一 finished 后 `deleteLater()` |
| 网络调用在 UI 线程（断网卡 15s） | 统计/周报/托盘检查全部线程化 |

- **教训**：**"能跑"和"能跑一年"是两件事**——长驻桌面程序必查：① 集合类有无上限 ② 线程/对象生命周期 ③ UI 线程有没有 IO

### 5.5 测试隔离坑（settings 单例）
- **现象**：全量测试时 `/api/messages` 返回 6 条而非 2 条
- **根因**：`lru_cache` 的 settings 单例 + `os.environ.setdefault`——第一个 import 的测试固化 DB_PATH，后续测试共享一库
- **修复**：断言改为"我插入的两条在且顺序对"，不断言全局数量
- **教训**：**对共享单例的测试，断言局部事实而非全局状态**

### 5.6 开机自启（任务计划 + pythonw）
- **方案**：任务计划 AtLogOn 触发 + `pythonw.exe`（无黑框）+ 崩溃重启 + 日志落盘
- **网络依赖**：Tailscale 需 `--unattended`（登录前自动连接），否则机器人启动时专线未就绪亮红灯
- **教训**：**自启的成败在启动顺序**——先网络（Tailscale），后应用（机器人/采集器），延迟启动避开开机高峰

### 5.7 自启排障三连坑（真实案例）
| 坑 | 现象 | 根因与修复 |
|---|---|---|
| PowerShell 编码 | 脚本中文全乱码、语法错误 | 无 BOM 的 UTF-8 被 PS 5.1 按 GBK 解码 → 存成带 BOM 的 UTF-8 |
| 路径多翻一层 | 任务报 0x8007010B，机器人不启动 | `Split-Path -Parent` 写了两遍，WorkingDirectory 少一层 → 错误码换算 + 查 Windows 错误码表定位 |
| pythonw 无声失败 | 任务失败但零报错 | pythonw 无控制台吞掉 stderr → 加文件日志 + sys.excepthook 黑匣子 |

- **教训**：① 错误码就是线索（2147942667 → 0x8007010B → "目录名称无效"）
  ② 无声环境（pythonw/后台服务）必须先装日志再排查 ③ 排障顺序：查任务配置（Actions）→ 查结果码（TaskInfo）→ 查日志（黑匣子）

### 5.8 无边框窗口缩放/移动三轮修复（v4.7，真实案例）
- **背景**：聊天面板 `setFixedSize` 写死，用户要求可缩放。三轮才修好，
  前两轮的根因分析还是错的——直到生产日志里的 AttributeError 实锤。
- **第一轮（失败，根因误判）**：外圈 6px 透明热区 + `startSystemResize`。
  拖拽即崩：`AttributeError: 'ChatPanel' object has no attribute
  'startSystemResize'`——**PySide6 根本不暴露这两个方法**（实测
  `hasattr(QWidget, 'startSystemResize') == False`，这是 PyQt6 独有
  API），而当时误判成"分层窗口透明像素点击穿透"。
- **第二轮（失败，修了个不存在的问题）**：加 alpha=1 底漆 + 窗口标志
  `WindowMinMaxButtonsHint`。API 都不存在，改这些自然毫无作用。
- **终局方案（确定性）**：① 卡片铺满窗口；② 八方向 `_ResizeHandle` 透明
  小部件**压在卡片外圈不透明像素上**（与按钮可点击同一原理，必然收到
  事件，光标内置）；③ 缩放/移动**纯本地几何计算**（begin/drag/end +
  最小尺寸钳制），完全不调用任何系统缩放 API；④ `resizeEvent`/
  `showEvent` 双保险布局把手（隐藏期间 resize 事件不投递，首次显示需
  补布局）。
- **连锁后果**：拖拽抛出的未捕获异常 + 用户反复重启 = 机器人今天 5 次
  "消失"（被当成"掉线"，实际网络 1800/1800 次健康检查全部 200，从未断过）。
  顺带加固：PAA-Robot 计划任务崩溃重启 1 → 3 次（与采集器对齐）。
- **教训**：① **PyQt ≠ PySide**——跨框架的 API 记忆会闹张冠李戴，
  `hasattr` 一查便知，查了就不至于三轮试错
  ② **生产日志里的异常栈是金线索**——第一现场比任何理论推演都可靠，
  排障第一步应该是翻日志而不是改代码
  ③ 用户报"掉线"未必是网络——进程崩溃、重启、卡死在用户眼里都是"掉线"，
  先分清是哪一种 ④ 隐藏的 Qt 窗口不投递 resize 事件，依赖布局的逻辑要
  在 showEvent 补一遍

## 六、思维模块（第 5 课后扩展）

统一模式：**检测（正则，零额外 LLM 成本）→ 存储（专属表）→ 注入（system prompt）**。

### 6.1 自省（纠正 → 教训）
- 检测"不对/错了/应该是/记住/以后…"→ 用户原话 + 被纠正的 AI 回复存 `lessons` 表
- 最近 5 条教训每次注入；周报统计"本周被纠正次数"

### 6.2 关切追踪（在意什么）
- consolidation 的 topics 自动更新 `concerns` 表（提及次数 + 最近时间）
- 聊天注入当前关切；每日小结提醒超 3 天未提及的话题（对应身份定义"主动预测需求"）

### 6.3 术语学习（口径一致）
- 检测"什么是 X"→ 术语 + AI 回复建档 `jargon_terms`；消息含已知术语自动注入解释
- 零额外 LLM 成本（复用已有回复）

### 6.4 风格学习（形式偏好）
- 检测正向反馈（很好/不错/就这样，短消息）→ 上一条 AI 回复存为范例
- 最近 2 条范例 few-shot 注入。与自省互补：自省管内容、风格管形式

### 6.5 每日小结
- 每晚 22:00：当天对话 + 行为统计 + 日志 → LLM 3-5 行小结 → 托盘通知
- 无活动的一天自动跳过（不烧 LLM）

### 6.6 "小月失忆"复盘（记忆系统断链教科书案例）

**现象**：给 AI 起名"小月"，重启机器人后再问"你叫什么名字"，它不记得。

**排查链**：
1. 怀疑重启丢数据 → 排除：记忆存服务器 SQLite，机器人只是客户端，重启不碰数据
2. 查数据在不在 → memories 有起名对话原文；4h 后 consolidation 会提炼成
   facts 三元组（"用户 给AI起名 小月"）→ 数据大概率在
3. 查注入清单（chat.py 的 system prompt 组装）→ 发现 **facts 从不注入聊天**
   （只喂周报/画像）；问名字时向量检索召回不到原文（"起名"与"叫什么"语义
   相似度不高）
4. 查自省兜底 → "起名/你叫"不在 CORRECTION_PATTERNS（只有不对/记住/以后…）→
   若用户原话不含"记住/以后"，不会进 lessons
5. 结论：**两个环节断链**——facts 提炼了却不注入；身份设定信号未被自省捕获

**修复**：
- `get_facts_injection()`：最近 10 条三元组每次注入（"关于用户的持久事实，务必记住并使用"）
- 自省信号词追加：起名/名字叫/就叫你/你的名字/叫你

**教训**：
1. **"存储了" ≠ "想得起"**——记忆链条 = 写入 → 提炼 → 注入，任何一环断开即失忆；
   本次断在最后一环（提炼了却不注入）
2. 用户报告里的"重启"是误导信号——根因排查要回到**数据流**，不留在现象层
3. 给系统加"记忆型功能"的检查清单三问：**写进哪张表了？会被提炼吗？每次注入了吗？**

### 6.7 "课程进度问答"四连坑（多轮对话完整复盘）

**现象**：问"项目进行到第几课"，机器人先后答错四种方式——
①"再确认一下"接不上 ②把图例"🔶 进行中"当真 ③只答六课漏掉进阶课 ④答不全还坚持旧说法。

**根因链与修复**：
| # | 根因 | 修复 |
|---|---|---|
| ① | LLM 调用只传当前消息，无历史 | 8 轮原文 + 窗口外摘要/原文兜底 |
| ② | 模型分不清"说明性文字"和"事实" | 图例显式声明"仅说明符号含义" |
| ③ | 状态事实靠检索（猜相关性） | 课程状态写 facts 三元组（每次必注入） |
| ④ | 多轮上下文延续旧错误说法（"执念"） | 修文档+facts 后新事实压过旧记忆 |

**教训**：
1. **确定事实走注入，不要走检索**——检索是"猜相关性"，状态/身份类事实必须每次必达
2. **多轮上下文是把双刃剑**：接得上话，也续得上错——模型会为自洽而坚持旧说法
3. 验证"答对了吗"要看**完整清单**（六课+进阶课），不只看"没提进行中了"

### 6.8 文档生成与简历优化（8-26）

- **文档生成**："写文档：标题X，内容：Y" → LLM 生成 Markdown → documents 表 + 同步知识库。
  教训：parse 命令要防"标题"两字混入标题（用户口语"标题RAG总结"无冒号）
- **简历优化**：知识库简历原文 → 简历专家 prompt（STAR/量化/JD 关键词/**禁编造**）
  → .docx 导出（python-docx 基础排版；精致排版仍是人的活）
- **.doc 转换**：antiword 对中文 .doc 有效且轻量（~100KB）；libreoffice 过重（~1GB），
  中文简历场景 antiword 足够。教训：**先试最轻的工具，不够再升级**
- **隐私边界**：简历含联系方式，进知识库后聊天会注入 LLM（第三方可见）——
  用户知情即可；但**绝不进 GitHub**

### 6.9 个性化问候（零 LLM 成本）

- 时段问候池（6 档随机）+ 日期周几 + git 提交数 + 周报安排提醒——纯规则组装

### 6.12 执行器白名单三重连环 bug + 目录排版/排序（8-27 上午）

- **白名单连续三次不生效的根因**：不是解析问题，是配置链路三层连环雷——
  ① `.env` 里根本没有这一行（记事本保存失败）
  ② cmd `echo >>` 修复时粘到上一行（文件末尾无换行）
  ③ 改对后又踩了 `EXECUTOR_ALLOWED_ROOTS` 与 pydantic-settings 字段名
  `executor_roots` 大小写/名称不匹配的坑
- 教训：① 配置文件改完**必须用程序读一遍验证**（findstr 看不到"粘行"，
  dotenv 一行命令看到真值）② 修改 .env 用 PowerShell 注意末尾补换行
  ③ 字段名与 env 变量必须逐字对照，别"看起来像"
- **list_dir 排版/排序升级**（用户验收反馈"排版排序不行"）：
  自然排序（大小写不敏感 + 数字按数值：f2 < f10）、文件夹在前、
  过滤 Windows 隐藏/系统项（$RECYCLE.BIN 等不再冒头）、全量显示
  （上限 300 条防病态目录）、去掉头部重复路径、空目录友好提示。
  desktop 与 collector 两条执行路径同步改 + 6 个回归测试固化。
- 教训：① **输出格式就是产品**——对齐用户心智模型（Explorer 习惯），
  别拿"能跑"当"好用"② 两处同源逻辑（本地直行/服务器队列）必须同步改，
  否则未来 QQ 通道会复现旧格式
- **验收时发现新问题：敏感目录名**——F 盘根目录有 `githu恢复码/` 文件夹，
  名字直接暴露内容。加"敏感名称预警"：列表命中 恢复码/密码/token 等
  正则时追加 ⚠️ 提醒行（零成本，规则即安全）。未来 QQ 通道列表会过服务器，
  这类预警就是脱敏的第二道防线。
- 教训：**验收输出要当安全审计做**——用户贴回的输出不只是"排版对不对"，
  还可能暴露不该出现的信息
- **排版二轮迭代**：用户反馈"逐行罗列 40 个文件夹像一面墙，不友好" →
  改紧凑分段式：📁/📄 分段标题 + 每段一行 `·` 分隔流式展示（44 项从
  46 行压到 10 行，自动换行）。聊天窗口不是终端，**逐行列表是最差解**。
- 教训：**信息密度要适配载体**——同一份目录数据，终端里逐行很自然，
  聊天气泡里就该折叠成段落；用户说"怪"先想呈现方式，别先怀疑排序

### 6.13 僵尸指令 + 结果游标未持久化（8-27 上午）

- **现象**：用户发"看看F盘的目录"，面板同时出现两条回复——第一条是本地
  执行器的新格式，第二条是"✅ 执行完成"的**旧格式**（还带着未过滤的系统目录）。
  用户判断"问题更加严重了"。
- **真相（查库定位）**：① 早上 09:10 面板还是旧版本时消息走到服务器队列，
  被**旧代码采集器**执行并把旧格式 result 存进 DB（done）② 面板的结果轮询
  游标 `last_executor_id` 每次启动都从 0 开始 → 这条历史结果**每次开面板都重播**。
- **修复**：① 服务器 pending 指令 30 分钟未领取自动标记"过期"，僵尸指令不再
  隔天突然执行 ② 面板游标持久化（QSettings），重启不重播历史结果
  ③ 清库：删掉那条测试指令和它回写的记忆消息 ④ 18 个回归测试全过。
- 教训：① **队列必须设 TTL**——异步通道的"延迟执行"对用户就是惊吓，
  默认丢弃好过默认执行 ② **轮询游标必须持久化**——重启重播等于把历史
  错当新闻 ③ 排查"多了一条消息"先查数据表时间戳（created/executed），
  数据会说话（原则 4）

- **清理**：全库扫描 → 简历实体替换（姓名/学校/公司/客户名 → 已脱敏，
  技能/经历保留）+ 通用模式打码（手机 131****2351 / 邮箱 wfy***@163.com
  / 公网 IP 101.33.*.* / 身份证）+ 受影响 13 块 9 条记忆**重新向量化** +

- **加固（防再犯）**：新增 `app/services/sanitize.py` 统一脱敏，四个入库

- 教训：① **存量清理和增量防漏必须一起做**——只清库不清管道，第二天
  数据又回来了 ② **向量库要跟着文本一起换**——改块内容不重建向量，

  ④ 备份快照是**脱敏死角**——删完数据别忘了删旧备份，否则攻击者读备份

### 6.15 第 13 课：执行器扩展——文件手 + 脚本脚（8-27 下午）

- **文件手**（copy/backup/move/rename）：复制/备份/移动/重命名，全部
  双路径白名单校验（源+目标都在允许根内才放行）；"备份"语义=时间戳
  子目录（永不覆盖），复制到已存在目录=放入同名文件，覆盖时显式提示。
- **脚本脚**（run_script）：仅桌面本地执行器支持——.py/.bat/.cmd，
  120s 超时强制终止、输出截断回传、CREATE_NO_WINDOW 无黑窗。
  **故意不做进服务器队列**：远程跑脚本=安全分级③，QQ 通道保持只读+
  文件操作。
- **表结构不升级的打包技巧**：双路径指令用 JSON 数组塞进单 target
  字段，unpack_paths 统一解包校验——零迁移成本。
- 教训：① **新增能力的默认安全档是"受限"**，白名单为空=全禁止，
  与第 11 课同一原则 ② **口语变体要覆盖全**（"把X移到Y/把X改名为Y"），
  测试先写用户会怎么说话 ③ 正则误吞闲聊（"帮我跑脚本"没有路径）用
  "目标必须像路径"的后置校验兜底 ④ **排障信号：新命令却走了服务器
  队列并回"未知指令类型" = 桌面端还在跑旧代码**（没 pull/没重启），
  先确认版本再怀疑逻辑

### 6.18 长文档入库（小说 ×2，8-28）

- **场景**：把两本 200 万字级小说（GBK）灌进知识库。
- **两个前置改造**：① embedding 分批调用（embedding-3 单次限 8 条，
  5276 块 = 660 批，逐批拼接 + 每 25 批日志进度）② ingest 增加
  `sanitize_content=False` 开关——小说里形似手机号的数字串会被脱敏
  误伤，长文本场景跳过。
- **实测账本**：229 万字符 → 5276 块 / 218 秒；168 万字符 → 3869 块 /
  158 秒；向量 1:1 零缺失；DB 17MB → 106MB；token 消耗约 20% 资源包。
- 教训：① **大批量入库必须分批 + 进度日志**，一次调用全量块必超
  API 上限且失败无从排障 ② **长文本和普通文档的入库策略不同**——
  脱敏规则对小说是噪声源，参数化开关比"一刀切"正确
  ③ 入库后必做抽样检索验证（剧情问题 top-k 命中 + 相似度），
  别信"跑完没报错"

### 6.19 小说问答调优：从"情节不完整"到"剧情因果可答"（8-28）

  ② 玩具 BM25（线性词频）→ 真 BM25：IDF + 词频饱和 + 长度归一，

  ⑥ 别名背景注入 LLM（跨名字指代的理解前提）

  一等公民**——事件发生时的名字和提问用的名字往往不同
  ③ **策划数据（设定卡）是 RAG 的合法组件**：权威事实直接注入，
  别指望小模型从叙事推理 ④ 端到端验收用"真实问题 + 禁聊天历史"，

### 6.20 常驻进程三灾：多实例堆积 / 控制台闪窗 / 崩溃空窗（8-28）

- **现象**：桌面挂着多个机器人 + 时不时命令窗一闪而过。
- **根因链**：① 看门狗判活查"命令行含 --robot"，但拉起命令不带
  --robot → 自己拉的孩子自己看不见 → 每分钟多拉一个（多实例堆积）
  ② 看门狗是计划任务每分钟跑 powershell.exe，即使 -WindowStyle Hidden
  控制台仍会闪现 ③ 无单实例保护，任务计划重启+看门狗+手动启动
  可叠加 ④ 崩溃后最长 60s 空窗（每分钟一轮判活）。
- **终局架构**：pythonw 常驻守护进程（supervise_robot.py）——零控制台、
  崩溃 3s 拉起、指数退避 3→60s 封顶、uptime 取证日志；main.py 单实例
  锁（QLockFile，PID 判活 60s 陈旧失效），重复实例**先锁后开窗**零闪退。
- **排障金律（supervisor.log uptime 判别）**：uptime <1s 且连续整齐 =
  锁冲突（有僵尸实例）而非崩溃；uptime >60s 后退出才考虑真崩溃，
  此时 faulthandler.log 是原生栈唯一证据。
- **Windows PowerShell 5.1 编码坑**：无 BOM 的 .ps1 按 GBK 解析，
  UTF-8 中文注释会把引号结构拆烂报语法错误——仓库所有 .ps1 必须
  带 UTF-8 BOM（提交前用脚本批量检查）。

### 6.21 记忆断层：确认过的设定为什么再问就忘（8-28 晚）

- **现象**：用户问"李羽为什么被盯上、性格底色是什么"，机器人答
  "我翻了记录，确实没找到"——但记录里明明有（#214 性格底色、
  #447 被盯上原因，均经用户确认，甚至问过"这些都记下了吗"）。
- **根因（记忆四层架构的断层）**：确认过的设定只进了第一层"原始
  聊天流"（语义检索召回，换个问法就丢）+ 第二层摘要（4h 后细节被
  压缩）；真正该待的第三层"永久事实 facts"（每次注入上下文）没有
  自动写入管道——**"确认"到"永久"之间是断的**。
- **修复链**：① `fact_extract` 自动提取管道：用户消息命中信号词
  （说过/记住/设定/能力/性格/关系…）→ LLM 提取三元组 → facts 按
  (subject,predicate) upsert（最新确认覆盖旧值）② 补录脚本
  `seed_story_facts.py` 从聊天记录人工核对回填 11 条已确认设定
  ③ 注入窗口 32→64（ASC 稳定排序）。
- **修复过程中抓到的隐藏 bug**：补录的 7 条事实写进了库却"答不上"——
  注入窗口只有 32 条且按 id ASC，新补的排在窗口外**根本没进上下文**；
  进度刷新"删了重插"还会让 id 不断后移加速挤出。修法：窗口放开 +
  刷新改 upsert 保 id 稳定。
- 教训：① **"记下了"要落到每次注入的永久层才算数**——只进原始
  聊天流的记忆等于没记 ② 验证记忆必须端到端（真实提问 + 检查
  注入内容），数据库里有 ≠ 会答出来 ③ 事实表要 upsert 不要
  delete+insert（id 稳定是注入窗口的隐性契约）④ 用户说"我说过了"
  是信号不是抱怨——先查记录里到底有没有，再判断是检索问题还是
  提取问题。

### 6.22 记忆三件套：混合检索 + 深挖兜底 + 延长留存（8-28 深夜）

- **目标**："记得聊过的每句话、更懂我"。存储层本来每句都在，
  短板是召回/留存/窗口。
- **三件套**：① 记忆检索从"单通道向量"升级为**向量 + BM25(IDF/饱和)
  RRF 混合**——与 6.19 小说知识库同款配方，精确词组（杀人变强/三四亩）
  不再漏召回 ② 弱命中（score<0.12）时**全库 2-gram 深挖兜底**——
  语义和 BM25 都没把握就逐条扫全部记忆按命中数排序，"每句话"的
  最后防线 ③ 留存 30 天→**365 天**、近轮窗口 8→**10**。
- **实测**：问"我说过李羽家里的田地是多少亩来着"——不只答出
  三四亩，还从最早对话里捞回"市价八到十二两/压价五两六两"细节。
- 教训：① **记忆和知识库共用一套检索配方**——6.19 调好的 BM25/
  RRF 直接移植记忆层，零试错 ② 检索要"三档位"：语义→精确词→
  全库扫描，每档有明确触发条件，不互相打架 ③ 留存策略是记忆
  质量的底线——召回再好，30 天删库也白搭。

### 6.23 更懂我三件套：每日画像 + 情绪感知 + 主动回忆（8-28 深夜）

- **目标**：从"记得"升级到"懂你"。
- **① 每日画像**：画像刷新从每周一次改为**每日 4:30 滚动更新**（读
  最近 7 天 facts），画像不再是一周前的你。
- **② 情绪感知**（零成本规则）：5 类情绪正则（疲惫/着急/烦躁/开心/
  低落）→ 风格指引注入 prompt——疲惫时回复简短少建议、着急时直给
  答案、低落时先共情。实测："今天累死了" → 机器人"赶紧歇着吧，
  别安排任务"。
- **③ 主动回忆**：系统提示词新增指令——注入记忆中与当前话题强相关
  且用户可能淡忘的内容，自然带一句"记得你之前说过…"，每次至多一次。
- 教训：① **"懂你"= 画像时效 × 情绪适配 × 记忆活用**，三条线互相
  独立可并行推进 ② 情绪检测先上规则，模型识别留到规则不够用时
  （零成本原则）③ 主动回忆要"至多一次"——多了变成显摆和噪音。

### 6.17 聊天区 v4.0 重构：布局级对齐 + 动画头像（8-27 晚）

- **踩坑链**：聊天面板左右对齐折腾了整整一天——CSS text-align 在
  Qt/Windows 上时灵时不灵、emoji 头像被宽字符推到行尾、markdown `<p>`
  内换行被压成空格、半透明面板透出背后窗口……每修一处又冒一处。
- **终局方案：放弃富文本对齐，改用 Qt 布局**——消息区从 QTextBrowser
  重构为 QScrollArea + QVBoxLayout，每条消息一行部件：你=右（蓝气泡）、
  小月=左（灰气泡+动画头像）。左右由 QHBoxLayout 保证，**布局级正确，
  不再依赖任何 CSS**。
- **动画头像**：RobotAvatar 自绘迷你小月（渐变头+LED 眼+天线+微笑），
  眨眼/呼吸/思考环绕粒子三套动画；等待回复时显示"正在想"行（头像变
  琥珀眼+粒子）→ 回复到达替换成真消息。
- 教训：① **渲染层的尽头是布局层**——当富文本的 CSS 表现反复翻车，
  不要再打补丁，直接把载体换成真正的 Widget 布局，一了百了
  ② 动画部件用"状态切换 + 单 QTimer 推进相位"，别为每个部件开线程
  ③ 离屏验证脚本从此成为 UI 交付的标配：头像双状态像素抽查 +
  气泡 x 坐标断言，全部自动可查

### 6.24 定时提醒 + 本地文件搜索：机器人第一次"主动找你"（8-29）

- **背景**：体验盘点后的第一批小功能（按约定顺序：小功能 → 小说增强 →
  QQ → 半自主）。两条线：机器人从"你问它答"升级到"到点主动触达"；
  文件搜索补齐"电脑里有但找不到"的场景。
- **① 定时提醒（全链路）**：
  - 命令解析零成本规则：`30分钟后提醒我喝水` / `明早9点提醒我开会` /
    `今晚8点提醒我看球` / `明天提醒我取快递`（缺时间默认早 9 点）；
    `我的提醒` 查看、`取消提醒：开会` 取消。解析不了就回用法提示，
    **不瞎猜时间**。
  - 存储：reminders 表（content/remind_at/status），时间统一 UTC 入库、
    Asia/Shanghai 解析——**存储和展示的时区要分开，混用必出跨天 bug**。
  - 推送闭环：桌面托盘每 30 秒轮询 `/api/reminders/due`，取到即弹窗。
    **取到即标 notified**：幂等设计（第 7 条原则），轮询丢了也只是少
    弹一次，不会同一提醒弹几十遍。
  - 回归坑：`明晚10点` 前缀一旦在正则里被剥离，就会算成上午 10 点——
    时段词必须和小时数**成对**交给解析函数。
- **② 本地文件搜索（桌面直行，零延迟不泄内容）**：
  - 句式：`帮我找包含todo的文件`（全白名单）/ `在F盘里找内容包含周报
    模板的文件`（指定目录 + 内容搜索）。
  - 护栏：跳过系统/缓存目录、深度 ≤12 层、每根目录最多扫 3000 文件、
    内容搜索只开文本扩展名 + ≤300KB + 最多开 150 个文件。全盘扫描
    不设限等于给机器人和自己上刑。
  - 误吞防护：**"目录必须像路径"**（盘符/斜杠/盘字）才认目录句式，
    "搜索淘宝里的switch"归网页搜索；全根句式必须有"包含/文件"标记，
    "搜索一下北京天气"归 LLM。搜索能力的第一原则：宁可不答，不可误吞。
- 教训：① **主动触达的最小闭环 = 对话设 + 轮询拉 + 取即消费**，
  不需要服务端推送通道也能先跑起来（QQ 推送可后接同一张表）
  ② 时间解析只覆盖高频句式，模糊的交给用户补一句，别用 LLM 猜时间
  ③ 文件搜索的价值在护栏不在算法——能扫 ≠ 敢扫
  ④ **更新代码 ≠ 更新运行中的程序**：机器人/采集器是两个 Python 进程，
  启动时把代码读进内存，git pull 只改了磁盘文件——不重启进程，新功能
  不会生效（本次"面板已是新版、采集器还是旧版"的诡异现场就源于此）。
  排查"更新后没生效"先确认进程重启，再怀疑代码。

### 6.25 小说写作增强：冲突检查 + 续写辅助 + 写作台账（8-29）

- **背景**：体验优化批次②。写作场景三件套：写之前怕设定打架、写的时候
  卡文、写完之后不知道自己写了多少。
- **① 设定冲突检查**：`检查设定冲突：<新写内容>` → 权威层 = 小说设定卡
  （关键词触发）+ facts 永久层（已确认设定），flash LLM 一次调用逐条比对，
  输出「你写的 ↔ 已有设定 ↔ 依据 ↔ 建议」。实测：故意写"十亩"，被对照
  「三四亩」抓出并给了修改建议；无冲突场景对照 38 条权威设定零误报。
  规则：只报确有冲突，疑似不报——**审校的第一美德是闭嘴**。
- **② 续写辅助**：`帮我续写：<当前段落>` → 设定卡 + 剧情背景（知识库
  检索 ± 邻域）+ 文风注入（参考《寂静杀戮》：短句/克制/动作感），
  续写 300~500 字。实测输出自动接住了"少爷管家逼地"的设定脉络。
- **③ 写作台账（零 LLM）**：`写作记录：第X章 N字` 入库，`写作进度` 汇总
  累计/近7天/今日/连续天数/最近记录。规则能解决的绝不上 LLM。
- 踩坑：最新章节"最近的记录"≠"最大的章节号"——写作会回补前章，台账要
  按 max(章节号) 算进度，按时间倒序展示记录，两件事分开。
- 教训：① **写作工具的杠杆点在"对照"**——AI 会编，设定卡是唯一不会
  跟着编的锚；冲突检查让设定卡从"检索资料"升级为"审校标准"
  ② 长文本命令（整章 3000 字）直接贴聊天即可，路径读取后续再接
  ③ 台账这类功能零成本原则：正则 + SQL 一天做完，别套 LLM。

### 6.26 消息全文搜索：聊天命令 + 面板检索弹窗（8-29）

- **目标**：聊天记录越攒越多，"我好像说过 XX"找不到原话。做关键词全文搜索。
- **设计取舍：找人话用 LIKE 不用向量**——用户目标是"找到我/小月说过的那句
  话"，关键词精确子串匹配 + 时间倒序，结果可预期；向量检索按语义跑偏
  反而不讨好。多关键词（空格/逗号分隔）做 AND 缩小结果集。
- **双入口**：
  - 聊天命令：`搜索聊天记录：田地`（零 LLM 规则，即时返回）
  - 面板 UI：🔍 检索按钮 → 弹窗（输入框 + 后台线程检索 + 纯文本结果）。
    结果区用 `setPlainText`——消息内容不渲染 HTML，**杜绝历史消息注入**。
- 实现：LIKE 全扫描 + 命中点片段截取（前 40 后 80 字）+ 北京时间展示；
  GET /api/messages/search 供 UI 复用。
- 教训：① **检索接口的定位决定实现**——找"原话"（确定性）和找"相关内容"
  （语义）是两种需求，前者 LIKE 更快更准 ② 展示用户历史内容一律纯文本，
  渲染层永远不信任数据层 ③ 弹窗三分支（命中/无结果/请求失败）都要有
  明确文案，网络功能不能只有"成功"一种形态。

### 6.27 情感连续性 A+B：情绪记忆层 + 负面连击降级（8-29）

- **背景**：6.23 的情绪感知是"单句级"——只听见你这句话的情绪。缺连续性：
  小月不记得你今天一整天不顺，也不察觉"我的回复让你更烦了"。按分档方案
  落地 A+B（纯服务端，零 LLM 增量）。
- **A 档 情绪记忆层**：mood_log 表，每条用户消息先过情绪正则、命中即入账
  （含命令类消息）。`今日情绪：烦躁×2、疲惫×1（最近一次在下午）` 注入
  prompt——小月整天延续情绪语境，不会下午还当你刚下班寒暄。
- **B 档 反馈闭环**：最近情绪连击，连续 2+ 轮负面（烦躁/疲惫/低落）→
  "倾听模式"注入：少建议、不安排新任务、先接住情绪、结尾轻问「需要我
  换个方式帮你吗」。开心/着急打断连击。
- **实弹验证**：连发两轮"烦死了/真服了" → 第三轮中性消息"算了，先不弄了"
  自动收到倾听式回复（先共情、不堆建议、真问了那句"需要我换个方式帮你吗"），
  mood_log 两条烦躁记录在账。
- **踩坑：连击有时效**——初版连击只算最近 N 条，昨天的烦躁会让今天一整天
  都在倾听模式里。加 2 小时新鲜度护栏：最近一次负面情绪超过 2 小时即过期。
  情绪状态是"快变量"，记忆是"慢变量"，两者生命周期要分开。
- 教训：① **情绪连续性 = 记录 + 回读**，规则层够用，别急着上 LLM 情绪识别
  ② 降级策略要"可退出"——连击、时效、打断信号三者缺一不可，否则一条负面
  情绪污染全天 ③ 倾听模式的下钩句（"需要我换个方式吗"）是闭环的出口，
  给用户一个把对话拉回正轨的把手。

### 6.28 情感连续性 C1+C2：情绪周报 + 小月体贴模式（8-29）

- **背景**：A+B 落地后补全分档方案的 C1（周报）+ C2（表情反馈）。
- **C1 情绪周报**：`mood.get_weekly_stats()` 聚合近 7 天 mood_log（分布 /
  负面话题 top5 / 3 小时桶高峰时段），周报生成后**零 LLM 确定性追加**
  「## 本周情绪」节——不依赖模型自觉，杜绝漏节或编数字。JD 实弹输出
  正常（烦躁×4、高峰 21-23 点、话题清单）。
- **C2 体贴模式**：`GET /api/mood/state`（streak_active + today_text）→
  托盘 60s 轮询（照抄提醒轮询模式）→ 悬浮球新状态 `caring`（暖橙主灯 +
  呼吸节奏放缓 0.06→0.04）。恢复：streak 结束自动回 online；服务器不可达
  保持现状不闪状态。
- 离屏冒烟 render_627_smoke：三皮肤 caring 变色断言 + 暖色像素采样 +
  恢复/容错两分支，全过。
- 教训：① **周报数据节要"确定性追加"而不是"提示模型写"**——LLM 会漏、
  会编，规则生成的节永远在 ② 状态展示的恢复条件与失败条件要对称设计
  （streak 结束恢复 + 网络失败保持现状），否则状态机会卡死或闪断
  ③ 桌面轮询模式第三次复用（提醒/周报/情绪）——同一 worker+定时器模式
  抽出来就是"轮询三件套"，模式复用比复制代码快。

### 6.29 健身减脂助手：台账 + 知识卡 + 身体数据（8-29）

- **背景**：用户要健身减脂支持。实测发现"聊天级"够用（模型自带知识 + 记忆），
  缺三层：身体数据 / 记录闭环 / 权威知识层。一次全补上。
- **① 身体数据进 facts**：用户确认的身高/体重/年龄/性别/健身基础/目标
  六条三元组（fact_extract 同款 upsert，幂等）。
- **② 健身台账（零 LLM，复用写作台账模式）**：`记录体重：70` /
  `训练记录：深蹲5x5` / `健身进度`——体重趋势（起始/当前/变化）、
  近 7 天训练、停练恢复提醒（无训练记录时给恢复期建议）。
- **③ 健身知识卡 15 张**：fitness_facts 表（仿小说设定卡），关键词触发
  注入、条目带出处年份——2024 食养指南 / 2025 肥胖诊疗指南 / 膳食指南
  2022 / WHO 2020 / ACSM 12 版。实测"平台期"问题自动接住权威要点且
  结合用户久坐画像。
- 踩坑：① 正则可选冒号会回溯——`训练记录：` 把冒号本身捕获成内容，
  需 lstrip 标点后再判空 ② 查询词与记录词重叠（"健身记录查询" 会被
  训练解析误吞）——解析器内显式排除，不依赖路由顺序。
- 教训：**"陪练"和"聊天"的区别不在知识，在数据与闭环**——模型本来就懂
  健身，缺的是用户身体数据、趋势记录、权威引用。知识卡引权威、台账
  出趋势、facts 存个体，三者齐了才是"懂你的教练"。

### 第 8 课 QQ 接入：借壳小白，小月三端合一（8-29 深夜）

- **背景**：QQ 是体验优化顺序的第③批。核心决策（用户拍板）：**借壳小白**
  （178903227，AstrBot+NapCat 已在 JD），小白人设让位、可回滚；**小白记忆
  不迁移**（wave_memory 数据保留冻结）。
- **主体分层**：账号主体（QQ 号借壳）→ 协议主体（NapCat/onebot）→ 人格主体
  （小月 FastAPI，唯一大脑）→ 执行主体（Windows 采集器）。QQ 只是小月的
  另一张嘴，与面板共享记忆。
- **架构选择：消息插件而不是换模型 provider**——AstrBot 插件 `astrbot_plugin_xy`
  在 `on_llm_request(priority=0)` 拦截：主人私聊直调小月 /api/chat（全功能），
  群聊一律 `should_call_llm(False)` 静默（**零个人信息暴露**——小月脑子里有
  小说设定/健身数据/项目信息，群里一个字都不能漏），陌生私聊同样静默。
  插件层白名单（owner_qq）+ AstrBot 平台白名单（id_whitelist）双保险。
- **提醒改推 QQ（唯一通道）**：NapCat 加 onebot HTTP server（127.0.0.1:3100），
  小月 scheduler 每分钟 `qq_push.push_reminders()` 调 `send_private_msg` 推主人
  QQ；桌面托盘提醒轮询退役。手机必达，不再依赖电脑开机。
- **远程指挥心跳提示**：执行器指令入队时查采集器心跳——不在线回复
  "电脑当前不在线：指令已入队，开机后执行（30 分钟内有效）"。
- 踩坑/运维要点：
  - **NapCat 容器重启会掉登录**，必须重扫二维码（本次实锤）——以后动
    NapCat 前先确认用户在手机旁；二维码约 1-2 分钟过期，重新取日志里的
    txz.qq.com 链接即可
  - AstrBot 插件配置在 `data/config/<plugin>_config.json`；停用插件 = 移动
    `data/plugins/<name>` 目录，数据不动即可回滚
  - 小月 QQ 推送配置（QQ_PUSH_URL/TOKEN/ADMIN_ID）只进 JD .env，QQ 号
    等个人数据不进仓库（测试用占位符 10001）
- 教训：① **借壳的最小代价方案是插件拦截，不是换模型**——provider 交换
  拿不到"群聊 vs 私聊"的上下文，隐私规则无从落地 ② **推送通道要"取即
  消费"**（复用 reminders 幂等），轮询丢了只是少推一次 ③ 账号体系里
  "主人"概念要在最靠近消息入口的地方校验（插件层），大脑层永远假设
  调用方可信。

### 6.30 全量代码审计整修：绕过、误吞、静默失效（9-01）

一次针对全仓的审计，逐条实测复现后修复。归类记在这里，因为这几个 bug
的成因高度一致：**判据分散在多处 + 没有测试锁住行为**。

- **扩展名黑名单被四类变形绕过（P0）**：三处执行器都用
  `os.path.splitext(t)[1]` 直接比黑名单，实测
  `x.bat.`→`'.'`、`x.bat `→`'.bat '`、`x.bat::$DATA`→`'.bat::$data'`
  全部漏判，而 Windows 打开时会剥掉尾点/尾空格、NTFS 数据流照常执行主文件。
  修复：判据统一到 `common/file_ops.is_blocked_open()`（先剥流名与尾部
  点/空格再取扩展名，含 `::` 一律拒绝）；服务端跑在 Linux 不能 import
  common，保留等价实现并用测试交叉锁死两者一致。
- **快捷启动器模糊匹配劫持 open（P0）**：`if k in key or key in k` 无长度
  下限，且 `try_launch` 在白名单校验**之前**执行。实测注册过白名单外的
  WeChat.exe 后，`打开微`、`打开信` 都能启动它；最隐蔽的是
  `打开F:/我的微信资料`——用户给了明确路径，却因含"微信"子串被劫持成启动
  exe，既没打开目录又绕过白名单。修复：open 通道走 `strict=True`
  （路径样式跳过别名解析 + 模糊匹配要求双方 ≥2 字符）；搜索模板通道
  不收紧，易用性不受影响。
- **命令正则误吞正常聊天（P1，最影响日常）**：`search_files` 早有
  `_looks_like_path` 护栏，`open/read_file/rename/copy/backup` 一个都没有。
  实测 12 条正常聊天 12 条全中："把这段话改成更正式的语气"→ rename、
  "备份策略到底怎么设计比较好"→ backup、"看看今天天气怎么样"→ read_file。
  后果分两级：多数被白名单挡住（用户问天气收到"🔒 超出白名单"），
  但 `open` 分支能通过服务端预检真的入队到 Windows。修复三层：
  ① 形态闸门（`_valid_single`/`_valid_pair`：双路径要求至少一侧含真实路径
  特征，句末语气词/疑问词直接判为聊天）② 低置信 open 不入队，落回 LLM
  当聊天回答 ③ 确认层兜底。
- **确认层（新增）**：破坏性动作（move/rename）与低置信 open 先问
  "需要我…吗？"，回复"确认/取消"再执行。做这层的原因是**正则治不了
  自然语言歧义**——"打开新世界的大门"与真别名形态完全相同，而服务端拿
  不到 Windows 本机的别名表，规则上无法区分。待确认状态存内存不入库
  （单进程部署，重启丢弃才是对的：隔天弹出的确认比丢弃更糟），
  3 分钟 TTL 短于执行器 30 分钟入队有效期。
- **两端脱敏规则漂移（P0）**：采集器与服务端各维护一份正则，实测采集端
  漏掉中文键名（`密码：hunter2` 原样上传）、全角冒号、GitHub/AWS/JWT
  三类 token；两端都漏 `手机13812345678`——根因是 **Python 里中文属于
  `\w`，中文与数字之间不构成 `\b` 边界**。反向误报也有：`版本 1.2.3.4`
  被打成 `1.2.*.*`。修复：合并到 `common/redact.py` 单一来源，数字类改
  `(?<!\d)/(?!\d)` 边界，IP 校验 0-255 且识别版本号语境。
- **git 游标按字符串比较带时区的时间戳（P0）**：`%cI` 含偏移，
  `'…T10:00:00+08:00' > '…T03:30:00+00:00'` 字符串为 True 而真实时序为
  False。游标被顶到未来时刻，其间提交**永久漏采**（游标已落盘，无补采
  路径）。修复：`fromisoformat` 转 aware datetime 比较，游标按 UTC 存储。
- **淘汰任务形同虚设（P1）**：只删 `kind='manual'`，而采集器产出的是
  app_usage/browser/git_commit——manual 一条都没有。实测 9 天累积 3359 行，
  且 `weekly_stats` 对该表做全表 `SUM(julianday(...))` 聚合。修复：按 kind
  分留存期（app_usage/browser 90 天、git_commit 730 天、未登记 kind
  兜底 180 天），顺带清理孤儿向量（线上实测存在 1 条）。
- **备份从不验证可恢复性（P1）**：注释写"保留 7 份约 60MB"，实测已
  461MB（每份 108MB，向量占大头），且同日重跑直接覆盖、从不校验能否打开。
  修复：热备到临时文件 → `integrity_check` + 关键表 COUNT → 通过才 gzip
  落位（113MB→42.8MB）→ 近 3 份日备 + 4 份周备。测试真的解压并查数据，
  而不只断言文件存在。
- **桌面端两处（P1）**：`_run_api` 是唯一没有重入保护的 worker，连点按钮
  会覆盖 QThread 引用致 GC 回收运行中的线程（本文件注释记载过的
  sizedFree 堆损坏成因）；`try_execute` 在 UI 线程同步跑，含 120s 脚本超时
  与 3000 文件扫描，面板会假死——项目本就有完整 worker 体系，只这条路绕过了。
- **采集器可靠性（P1）**：`.env` 路径写成 `parents[2]`（仓库外层），
  从未被 pydantic 读到，只因 main.py 先跑 `load_dotenv` 才碰巧生效；
  `cache_dir` 定义了却没接线，按 CWD 解析（开机自启时是 System32）；
  心跳循环首行就 sleep(300)，启动后 5 分钟服务器判定"电脑不在线"；
  缓存重放无论成败都 unlink，断网叠加磁盘满会静默丢整批历史事件。
- **顺带的真实收益**：`update_summary` 是带 bug 的死代码（少传一个形参、
  零调用方），而 consolidation 直接 UPDATE 不同步 FTS —— 意味着**提炼出来
  的 summary 一直检索不到**。修好签名并接进 consolidation 后，摘要进入
  BM25 索引；另外聊天主路径对同一条消息 embed 了两次（一次检索、一次
  入库），复用后每轮省一次网络往返与 token。
- 教训：① **同一判据出现在三个文件里，等于三个都不可信**——安全判据必须
  单一来源，跨进程无法共享时用测试锁死一致性 ② **"解析成功"不等于
  "该执行"**，自然语言入口需要形态闸门 + 置信度 + 确认三层，靠加正则
  只会越补越漏 ③ **淘汰/备份这类后台任务要按真实数据验证**，注释里的
  "约 60MB"和现实的 461MB 差了 7 倍都没人发现 ④ **中文场景下 `\b` 不可用**，
  凡是中英混排的正则都要单独验中文相邻情形 ⑤ 死代码不是无害的——
  它掩盖了"摘要检索不到"这个功能缺陷。
- 测试：302 → 421（+119），新增覆盖扩展名变形、误吞语句、launcher×白名单
  劫持、确认层全流程、git 游标时区、通道停滞告警、缓存重放、多 profile
  浏览器采集、备份可恢复性。

### 6.31 测试把生产库清空了：lru_cache 单例吃掉了 DB_PATH（9-01）

本轮最贵的一课，而且是我自己踩的：跑了一次全量测试，**真实库被清空**——
`memories` 650→10、`knowledge_chunks` 3602→2、`facts` 53→1、
`behavior_events` 3157→1，残留的全是测试数据。

- **根因**：14 个测试文件都靠 `os.environ.setdefault("DB_PATH", "/tmp/x.db")`
  做隔离，但 `conftest.py` 在**收集阶段**就 `from app.config import settings`，
  而 `get_settings()` 带 `@lru_cache`——单例早已实例化，此后改环境变量完全
  无效，`settings.db_path` 始终是 `./data/assistant.db`。那些 fixture 里的
  `DELETE FROM memories` / `DELETE FROM knowledge_chunks` 于是一直跑在真实
  数据上。有个 fixture 的注释还写着"settings 单例导致多测试文件共享一库"
  ——作者知道在共享，但不知道共享的是**生产库**。
- **为什么一直没暴露**：这些用例多数只 INSERT，灌进去的脏数据不显眼
  （线上 `lessons` 里那 16 条重复的「测试教训」就是这么来的，一度被当成
  业务 bug 排查）。真正引爆是我为迁移写的用例里有一句 `DROP TABLE lessons`。
- **修复不能靠自觉**：全部改成
  `monkeypatch.setattr(settings, "db_path", str(tmp_path / "test.db"))`，
  外加 conftest 两层护栏。第一层 `pytest_configure` 把默认库从生产库挪开
  （fail-safe，即使某个文件完全忘了隔离也拿不到真实库）；第二层
  `pytest_sessionstart` 在 `connect()` 上装拦截器，**真正打开连接那一刻**
  校验，指向生产库直接 RuntimeError。
- **我第一版护栏是错的**：写成 autouse fixture 的前后断言，探针测出拦不住
  ——monkeypatch 是函数级的，会在 autouse fixture 的 teardown **之前**把值
  还原，后置断言永远看到干净值。这是典型的 time-of-check vs time-of-use：
  检查点和使用点之间隔着状态变化，检查就是假的。改成在 `connect()` 里
  校验（time-of-use）才无从绕过——写完护栏必须写一个"故意违规"的探针验证
  它真的会失败，否则你只是加了一段自我安慰的代码。
- **恢复**：`data/backups/assistant-20260901.db`（每日 03:00 热备份）完整
  可用。先把损坏库另存为 `assistant-corrupted-*.db` 留对照再覆盖，逐表核对
  确认 03:00 之后无真实增量（那 18 条重复的 `下午2-5点调RAG性能` work_log
  全是测试产物），零真实数据丢失。**6.30 那条"备份要验证可恢复性"的教训，
  三天后就用上了。**
- 教训：① **配置单例 + 环境变量 = 静默失效**，凡是"设个环境变量就隔离好了"
  的写法都要验证它真的生效，而不是看起来生效 ② **危险的默认值要在机器层面
  堵住**，不能写在文档或注释里靠人记得 ③ **护栏本身也要被测试**，没有探针
  验证过的护栏不算护栏 ④ 跑破坏性操作前后都要留校验点（我现在每次全量测试
  前后都比对生产库 md5）⑤ 出事后**先取证再动手**，第一反应"重跑一次看看"
  会把现场毁掉。

### 6.32 拟人化：让她有"自己的状态"（9-01）

前八条注入通道全是"关于用户"的，小月自己没有任何连续性——每轮对话里的她
都是刚出生的。这轮补的四件事，共同点是**都不新增 LLM 调用**：

- **教训去重与分级**：`lessons` 加 `UNIQUE(content)` + `kind`。实测线上
  52 行只有 7 条不同内容，`LIMIT 5` 的注入窗口被同一句话的副本占满，
  「你就叫小月吧」这条**定义她身份的设定反而进不了 prompt**。现在 identity
  类（起名/定身份）不占普通配额、永久排最前。
- **隔日跟进**：情绪连击只管当轮（2h 后清零），但真人记得昨天。
  昨天负面 ≥2 条且今天还没开口时，提示轻轻问一句；判定"今天没聊过"直接用
  `mood_log` 本身，不新增表。问过即止——**关心问两遍就变成催促**。
- **自我状态**（`self_state.py`）：今天聊了几轮（熟络度档位）、距上次多久
  （久别）、最近是否被纠正过（更谨慎）。访客路径不读 `lessons`，保持单用户
  表隔离。
- **主动开口**（`initiative.py`，默认关闭）：补的是一个真实断点——每晚的
  《今日小结》和 `get_stale_concerns` 算出的搁置话题此前**只写进库，没有
  出口**（`send_private_msg` 全项目只有 2 处调用，都在推提醒）。给它出口的
  同时，把"不打扰"写成代码约束而非自觉：每日 1 条、23:00-08:00 静默、连续
  3 次无回应降频到每周 1 条、同话题只问一次、推送失败不入账可重试。
- 教训：① **拟人化不等于加语气词**，缺的是"她自己的连续状态"这一维
  ② 注入窗口是稀缺资源，**没有去重的追加写会让最重要的那条被挤出去**
  ③ 行为上的重大改变（从"你问她答"到"她会找你"）要默认关闭 + 硬上限，
  让用户自己决定何时开。
- 测试：421 → 459（+38），覆盖去重/迁移幂等/identity 优先、隔日跟进的
  触发与静默、自我状态各档位与访客隔离、主动开口的四条硬约束。

### 6.33 token 记账与对话回归集：先量再优化（9-01）

被问"回归集 10 题要花多少 token"时才发现，**项目从来没记过 usage**——
只能靠字符数估算。而估算在这里误差极大：`cached read` 单价比输入便宜
**30 倍**（zen 上 $0.007 vs $0.22 /M），缓存命中率不明就等于成本不明。

- **记账（`llm.py`）**：每次调用累加真实 usage 到进程内计数器，
  提供 `get_usage()` / `reset_usage()`。只记内存不入库——记账本身不该
  产生写库开销。缓存字段各家不一（DeepSeek 用 `prompt_cache_hit_tokens`、
  OpenAI 系用 `prompt_tokens_details.cached_tokens`、中转可能返回空 `{}`），
  三种形态都要兼容且不能因缺字段炸掉主流程。
- **实测数据**：单轮聊天输入约 6,000 tok / 输出约 300 tok；10 题回归集
  一次 0.09 元（高峰）或 0.045 元（非高峰）。**前缀缓存实测命中 31%-76%**
  ——`chat.py` 里"稳定档案区放前面"那句注释不是理论，是真在省钱。
- **回归集（`benchmarks/chat_regression.py`）**：TESTING_GUIDE 里挂了很久的
  "建议实现"。10 题 + 关键词判据 + 通过/退化表格，`--dry-run` 跑临时库。
- **判据自己先错了两题**：她答"我不太**确定**"，我判据写死"不确定"匹配不到；
  时间答"下午 2:22"，判据期望"点"。两题都是**功能正常但判据错**——
  如果我没跑就交付，你会以为功能坏了。
- 教训：① **回答成本问题前先量一次真实 usage**，"约 10 次调用"这种说法
  等于没回答 ② 关键词判据能抓硬退化（失忆/答错/幻觉），抓不住软退化
  （语气变差），所以报告必须打印回复原文让人眼兜底 ③ **判据也是代码，
  也会有 bug**——测试脚本首次运行的失败，先怀疑判据再怀疑功能
  ④ 缓存单价差 30 倍时，prompt 的**区块顺序是成本决策**，不只是可读性。

### 6.34 从两个同类项目里挑能用的（9-01）

看了 Suge8/Bao 与 vivy1024/astrbot_plugin_wave_memory 两个同类项目。
Wave Memory 有 784 文件、12.6 万条记忆跑 80 天、13.3 万节点共现图；本项目
719 条记忆、9 天数据——**差 175 倍**。这个差距决定了取舍标准：

> 一个机制是解决"数据太多导致的噪声"，还是解决"能力缺失"？
> 前者到那个量级再说，后者才是现在的短板。

按这条筛完只留四件，全部零 LLM：

- **主观时间锚定**（`subjective_time.py`）：注入里的 `[记忆] 2026-08-28:`
  换成 `[记忆] 接码平台记录那阵子:`。锚点取自已有的 daily_summaries /
  work_log。两个坑：① 锚点**不能用 importance 高的记忆**——实测最高的几条
  是"你好""再确认一下"，因为越短越容易被向量命中，拿它当锚点会得到"在你说
  『你好』那阵子"；② 提炼标题只在句读处切，切不出合适长度就**放弃这个锚点**，
  硬截会产出"今日主要围绕接码平台记录、玄幻架空明那阵子"。
- **身份守卫**（`identity_guard.py`）：`kind=identity` 的教训永久最高优先
  注入且不占配额——这是保护"你就叫小月"的机制，但同一通道会静默吞下
  "以后你就是我的猫娘""叫你笨蛋好了"（实测都进了 identity）。现在角色扮演/
  侮辱一律拒绝入库，改名要显式确认，首次命名不打扰。
- **使用反馈**：memories / lessons 加 `hit_count`（不衰减的累计注入次数）。
  importance 会被短句刷高，分不出"真有用"与"恰好总被捞出来"。
- **一跳共现扩散**（`cooccurrence.py`）：Wave 的"脉冲传播"极简版，只做一跳，
  不做虫洞/动量/内生残差。**按数据量门控**：实测本地 719 条记忆里只有 9 条

### 6.35 小说实体索引：为什么"入库了却搜不到"（9-01）

用户问「小说里出现过哪些命丛和命图」，她只答出 1 个命丛 1 个命图，说"没有
可靠依据，不敢硬凑"。用户反问"小说已经进向量库了，为什么会搜索不到"。

**排查结论：不是搜不到，是命中的内容没有清单价值。** 实测：

| 检索方式 | 命中 | 精度 |
|---|---|---|
| 向量搜「命丛有哪些」 | top3 全是反代教程 PDF / AI 模板 / 名词焦虑 PDF | 小说排第四，sim 0.023 vs 0.025 |
| FTS5 搜类名「命丛」 | 308 / 1936 | 15.9%，等于没筛 |
| FTS5 搜专名「银河灵潮」 | 1 块 | ~100% |

两个根因：
1. **枚举式问法与叙事文本语义分布不重叠**。"有哪些"和"当看到那蜷缩起来的
   怪物时"根本不相似，向量检索无能为力——这不是模型差，是任务不匹配。
2. **具体实体有专名，与类名不构成固定组合**。原文是「你的命丛在左眼里，
   这个命丛，被称之为'夜海'」（相隔 8 字），也有「命丛夜海」直连、
   「就剩下夜海这个命丛了」倒序。正则抽不出来（「XX的命丛」模式的输出是
   "而不同/测一测我/单一"这类噪声）。而且**搜类名必漏**：含「夜海」的 69 块
   里有 26 块不含"命丛"二字。

而且她收到的注入确实是 5638 字符，但里面全是冥王蛇登场时"马儿嘶鸣着朝后
退去"这类场景描写——**真正有信息量的「四种命图分别是…要求81个/61个/40个/
28个」被挤到末尾或截断了**。

**方案：先建专名索引，把类名匹配转成专名匹配。**

- 阶段一（一次性）：命名句定位（纯规则）把 308 块缩到 44 块 → LLM 只做
  "从候选里挑真专名"这一件事 → 跨类去重 → 用户确认。
- 阶段二（每次提问，零 LLM）：意图识别 → 专名精确召回 → **块内定位裁剪**
  （只取含专名的句子±1句，治的就是"4500 字里只有 300 字有用"）→ 聚合去重
  → 预算裁剪 + **完整度报告**。

效果：命丛 1 → 27 个、命图 1 → 8 个，每个带作用描述；并能说清"原文提到
七大神命丛，目前确认 N 个，缺口是资料本身不全"。

**四个实测踩坑**：
- **中文弯引号**：`NAMING_PATTERNS` 的引号字符类只写了 ASCII 的 `'` `"`，
  而原文用的是 `‘’`（U+2018/2019）——命名句**全部漏匹配**，候选块从 44 掉到
  16，实体少抽 64%。这个 bug 是单元测试照出来的（我先写了断言"该命中 1 块"，
  实测返回 0 块）。
- **枚举句漏抽**：命名句模式只覆盖"逐个介绍"的写法，漏掉作者一次列举多个的
  句子（「这四种命图分别是鬼眼黄泉天，清净焰光城，夜亡君主以及白帝极光剑」
  ——4 个只抽到 2 个）。补了枚举句直抽层，但它噪声极高（命丛 488 个候选多是
  句子片段），所以**只用它定位块并作为 hints 交给 LLM 判真假，不直接入库**。
- **共现频次判断归属会错**：「鬼眼黄泉天」是命图，但它需要 81 个命丛，正文里
  与"命丛"共现 85 次、与"命图"仅 31 次——按频次判会归错类。改用枚举句作直接
  证据（#385「这四种命图分别是鬼眼黄泉天…」），频次只作兜底。
- **集合表述要锚定类名**：`[一二三四五六七八九十]大X` 不加约束会抽出
  「一大口鲜血」（出现 9 次，比真正的「七大神命丛」5 次还多）、「四大天王」。

- 教训：① **"入库了搜不到"往往不是检索坏了，而是任务与检索方式不匹配**
  ——枚举式提问天生不适合向量，先看命中内容再改参数 ② 索引与答案要分清：
  **存实体名（客观、不随提问变化）可以复用，存问答结果会随提问维度爆炸且
  互相矛盾** ③ 正则在中文小说上极不可靠，正确用法是"规则定位 + LLM 判真假"，
  让规则只负责缩小范围 ④ 中文标点（弯引号/全角冒号）是正则的常见盲区，
  本项目已第二次栽在这里（6.30 是全角冒号）⑤ 完整度报告比完整答案更有价值
  ——**缺口可见，她才能诚实说"缺什么"而不是笼统地推回给用户**。
- 测试：548 → 597（+49）。

## 七、通用工程原则（这几天沉淀下来的）

1. **兜底分支要能验证主路径**——fallback 会掩盖主 bug
2. **静默失败必须留痕**——except: pass 是排障黑洞
3. **推送系统要幂等**——消费端永远假设"可能收到重复"
4. **验证看数据不看日志**——日志无报错 ≠ 数据正确
5. **修复必配回归测试**——当天发现的 bug 当天固化测试
6. **排障先确认对象**——IP、端口、环境、账户，一层层排除
7. **文档脱敏**——IP/密钥/token 只进本地笔记，不进仓库
8. **状态在过程中记录**——别在结束时反推（拖拽判定）
9. **长驻程序三查**——集合上限 / 对象生命周期 / UI 线程 IO
10. **交互分级**——高频动作不绑定重操作（单击≠弹窗）
11. **模式复用**——同类能力（检测→存储→注入）抽成同一模式，第五个模块半小时搞定
12. **零成本优先**——检测用正则、术语复用已有回复，能用规则就不烧 LLM
13. **配置必验真值**——改配置后让程序读一遍输出真值，肉眼 grep 不算数
14. **返回成功 ≠ 真的执行**——委托给系统的调用（startSystem* 等）可能静默
    无效，关键交互要有本地确定性实现兜底，或干脆不用委托
15. **可点击区域只能由不透明像素保证**——半透明窗口上任何"透明也能点"的
    设计都是在赌合成器行为；可交互控件必须叠在不透明内容之上
16. **安全判据必须单一来源**——同一规则散落在多处时，一处漏改就等于全线
    失守；跨进程实在无法共享，就用测试交叉锁死两份实现一致
17. **"解析成功"≠"应该执行"**——自然语言入口要分三层（形态闸门 → 置信度
    → 用户确认），单靠加正则只会越补越漏
18. **中文场景下 `\b` 不可用**——中文属于 `\w`，中文与数字/字母相邻处没有
    词边界；中英混排的正则必须单独验证中文紧邻的情形
19. **后台任务要按真实数据复核**——注释写"约 60MB"、实际 461MB 却无人发觉；
    淘汰、备份、清理这类没人盯的任务，要定期核对真实表行数与文件体积
20. **备份的唯一价值是能恢复**——只断言"文件生成了"毫无意义，必须真的
    解压、打开、查一次数据；不校验的备份等于不知道有没有备份
21. **测试必须证明自己碰不到生产数据**——"设个环境变量就隔离了"要实测验证
    （配置单例 + lru_cache 会让它静默失效）；危险默认值在机器层面堵死，
    不写在注释里靠人记得
22. **护栏本身也要被测试**——写一个"故意违规"的探针确认它真的失败；
    没被探针验证过的护栏只是自我安慰。注意 time-of-check ≠ time-of-use：
    检查点与使用点之间隔着状态变化，检查就是假的
23. **出事先取证再动手**——第一反应"重跑一次看看"会把现场毁掉；
    破坏性操作前后各留一个校验点（如比对文件 md5）
