# QQ 群聊 @ 判定参考（历史实现摘录）

本文件在删除 `qq/astrbot_plugin_xy/` 前摘录其中值得复用的判定语义，供后续 QQ 接入重构参考。**这里只记录设计意图和判据，不是可运行代码**；原实现依赖 AstrBot 的事件/组件对象，新链路需改为直接读 OneBot v11 消息段。

原始来源：`qq/astrbot_plugin_xy/main.py` 的 `group_triggered` / `group_rate_limited`（已于 2026-09-15 随目录删除，可在 Git 历史中查阅）。

## 1. 为什么值得保留这套判据

这套判定是 **fail-closed** 的：任何无法确认"这条消息确实在叫机器人"的情况都不触发。被删除的 MaiBot 走的是相反路线（先进 Planner 再由模型决定），结果出现"频率门连带屏蔽 @"的耦合问题。重构时应保留 fail-closed 方向。

## 2. 触发条件（满足任一即视为明确唤醒）

按原实现的判定顺序：

1. **显式前缀**：文本以配置的唤醒前缀开头。
2. **框架唤醒标记**：事件自身声明"被 @ 或命中唤醒词"。
3. **At 组件命中本账号**：消息段里存在 At/mention，且其目标 ID **等于机器人自己的账号**。
4. **Reply 组件指向本账号**：引用回复的目标消息，其发送者是机器人自己——视为对上一条回复的追问。

## 3. 明确不触发的情况（关键）

- **拿不到机器人自己的账号 ID 时直接不触发**。这是整套判据的核心：无法确认目标就不回应，宁可漏答不可乱答。
- At 的目标是别人 → 不触发。
- Reply 引用的是其他群友的消息 → 不触发。
- 仅在纯文本里出现机器人名字 → **不触发**。名字匹配误唤醒率高，历史上 MaiBot 的"提及必回"默认关闭也是同一原因。

## 4. 组件字段兼容性经验

原实现踩过的坑，重构时仍需注意：

- **组件类型名不稳定**：同一种 At 组件在不同框架/版本里可能是枚举、字符串或类名，原实现同时比对 `type.value`、`type.name`、类名末段并统一小写。改用 OneBot 原始 JSON 后这个问题消失（`type` 就是 `"at"`），是改造的收益之一。
- **目标 ID 的字段名不统一**：原实现依次尝试 `qq`、`target`、`user_id`、`sender_id`、`id`，再回退到 `sender` 子对象。OneBot v11 里 At 段固定是 `data.qq`，Reply 段只给 `data.id`（被引用消息 ID），**需要再查一次消息详情才能拿到原发送者**——这一步失败时应按 fail-closed 处理，不触发。

## 5. 限流语义

原 `group_rate_limited` 的设计取舍值得沿用：

- **冷却默认关闭（0 秒）**。理由写在原注释里：被点名提问必须能得到回答，群聊机器人被 @ 却沉默，对用户就是"坏了"。
- **保留每小时上限**（原默认 30），定位是**滥用闸门**而非正常对话节流。
- 需要压制刷屏时才显式配置冷却，不要用冷却做常规节流。
- 按群维度独立计数，并对记录的群数量设上限，避免无界增长。

## 6. 与服务端契约的衔接

服务端 `POST /api/chat` 已有 `group_directed` 参数，语义正是"这条消息是否明确对机器人说话"。上述判定的输出应直接映射到该字段，避免网关与服务端各判一次（这正是旧 AstrBot + 服务端两层重复判定的问题所在）。

相关服务端实现：
- `server/app/chat/context.py` — `group_directed` 与群作用域身份校验
- `server/app/auth.py` — QQ 身份 HMAC 签名头
