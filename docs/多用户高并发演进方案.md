# 多用户高并发演进方案（设计稿 · 待确认）

> 问题：项目要从小月个人助手（单用户 + 少量访客）演进为多用户、高并发服务，
> 应该怎么改、是否支持。
> 版本：v0.1（方案评审稿，未实施）
> 结论先行：**支持，但需要分层改造；现状是"单进程 + 单写者 SQLite + 进程内状态"，
> 撑几十人低并发没问题（QQ 单 bot 本身是天然限流器），真高并发必须按 P0→P2 演进。**

---

## 一、现状定性（逐条对照代码）

| 组件 | 现状 | 高并发下的问题 |
|---|---|---|
| Web 层 | uvicorn 单进程（run.py 未开 workers） | 单核事件循环，吞吐上限低 |
| 数据库 | SQLite WAL + 同步 sqlite3 驱动（线程本地连接缓存） | ①单写者：高并发写"database is locked"②**同步 SQL 在 async 路径直接执行，阻塞事件循环**——这是最优先的瓶颈 |
| 向量检索 | sqlite-vec vec0，按用户过滤靠"KNN 取 k=100 再 Python 过滤" | 用户数上去后过滤后命中率下降，k=100 不够 |
| 全文检索 | FTS5 + 应用层 2-gram | 随库增长 OK，但写并发受限 |
| 定时任务 | APScheduler 在 API 进程内 | 多 worker 部署会重复执行（consolidation/周报跑 N 份） |
| 访客限流 | 进程内 dict（滑动窗口） | 多实例各自计数 = 限流失效 |
| 缓存 | 进程内（分域词表、动态类名、连接缓存） | 多实例不一致 |
| 后台任务 | asyncio 任务 + _bg_tasks 引用集 | 进程重启即丢、无重试 |
| 鉴权 | 单共享 API_TOKEN | 多端多用户需要分级 token |
| QQ 入口 | 单 bot（178903227）+ AstrBot 单实例 | QQ 单号消息量有限，天然限流；多 bot 需插件多实例 |
| 画像/记忆隔离 | 已按 user_id 隔离（v0.4）✅ | 应用层多用户已就绪，是最大利好 |

## 二、容量基线（实测外推，供决策）

- 当前：单用户 + 少量访客，每轮对话 20+ 次同步 SQL、1-2 次 embedding、1 次 LLM
- 单进程现状可支撑：**约 50-200 并发连接、每秒几轮对话**（LLM 延迟主导，
  SQLite 读多写少时不是首瓶颈）
- 目标超过此量级 → 必须走 P0

## 三、分期方案

### P0：单进程内优化（不改数据库，先压榨存量，约 1-2 天）

1. **DB 访问全异步化（最高优先）**：所有 async 路径的同步 SQL 包
   `asyncio.to_thread`（或换 aiosqlite 连接池）——消除事件循环阻塞，
   吞吐可翻数倍，改动集中在 database.py 的连接上下文
2. **embedding 缓存**：按文本哈希缓存向量（同/近查询省 API 调用与延迟，
   也保护 embedding 配额）
3. **写操作批量化**：消息入库 + FTS + 向量三条 SQL 合并事务（已部分如此）
4. **WAL/busy_timeout 调优**：checkpoint 被动化、写重试封装
5. **限流落库**：访客限流从进程内 dict 移到 DB 表（为 P1 多实例铺路）
6. 压测基线：locust 场景（聊天 80% / 检索 20%），记录 QPS 与 P95

### P1：多实例 + 状态外置（约 3-5 天）

1. **调度器单实例化**：API 与 scheduler 拆两个进程（ENABLE_SCHEDULER 环境变量，
   只在一个实例开）；consolidation/周报/淘汰不再重复
2. **状态外置**：限流、动态类名缓存、候选池锁 → Redis（或数据库表 + 原子操作）
3. **API 多 worker**（uvicorn workers=N），前置 Nginx 负载均衡
4. **后台任务队列化**：事实提取/黑话推断/实体抽取/整合 → Redis 队列（arq/rq），
   失败可重试、进程重启不丢
5. **鉴权分级**：每端独立 token（QQ 插件/桌面/Web），全局 + 每用户双层限流
6. **SQLite 写瓶颈缓解**：写操作串行化（单写者队列）或读写分离（只读副本）

### P2：数据层替换（真正的高并发，约 1-2 周）

1. **SQLite → PostgreSQL + pgvector**：
   - 迁移：表结构平移（8 张用户态表已带 user_id，直接映射）、
     vec0 → pgvector（embedding 列 + HNSW 索引）、FTS5 → 应用层 2-gram
     倒排表不变（在 pg 上跑得更快）
   - 连接池 asyncpg；事务语义重写（去线程本地缓存）
2. **向量按用户过滤**：pgvector 支持 `WHERE user_id=? ORDER BY vec <=> ?`，
   告别"KNN 取 k=100 再 Python 过滤"的 hack
3. **检索层微调**：实体索引/分域路由全部 SQL 化已有基础，直接受益
4. **读写分离 + 分库**：按 user_id 哈希分库（用户态表全带 user_id，
   分库条件已具备）
5. **可观测**：决策轨迹/成本画像已就绪（P0 成果），加 Prometheus 指标导出
   （仅此阶段才值得引入——单机阶段保持轻量）

## 四、QQ 端的多用户边界（与 Web 端解耦）

- 单 QQ 号天然限流（平台限制），**不需要**为 QQ 做高并发
- 若要多 bot：AstrBot 插件多实例 + owner 白名单多号，服务端已支持
  （user_id = QQ 号，无改动）
- 高并发需求主要来自 Web/API 端（如果将来开放网页版小月）

## 五、迁移与验证策略

1. **影子库双写**：P2 切库前，SQLite 与 PostgreSQL 双写 1 周，数据对账后切换
2. **回归基准**：现有 801 个测试全量过 + 路由评测基准（P0 成果）在新栈复跑
3. **压测验收**：目标 QPS/P95 写进测试（locust 场景化），达标才上线
4. **回滚预案**：双写期保留 SQLite 全量备份，可一天内回退

## 六、明确不做（防过度设计，延续既定原则）

- 不引入微服务拆分（单体多 worker 足够到百万级对话量）
- 不上 Kafka（arq/Redis 队列足够）
- 不重写检索算法（分域/实体/自愈体系已证明有效，平移即可）

## 七、决策点（实施前需拍板）

1. 目标规模：多少注册用户 / 目标 QPS？（决定走到 P0 还是 P2）
2. 入口形态：Web 端开放注册，还是保持"QQ + 桌面"为主？
3. 数据合规：多用户规模化后，记忆内容的隐私/删除权需求（GDPR 式"遗忘权"）？
