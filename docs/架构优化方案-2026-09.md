## 1. 聊天热路径：同一 query 发两次 embedding API + retrieve() 全程串行

> **✅ 已实施。**

- **问题**：`retrieve()` 里 `memory.search`（core/memory.py:345 embed 一次）与
  `knowledge.search_knowledge`（core/knowledge.py:183 `_vector_search` 再 embed 同一串）
  对**同一个 search_query** 各打一次 embedding API（单次 218~1244ms）；随后
  别名/实体/注入全部串行（chat/retrieval.py:321-506）。
- **方案**：① `core/embedding.py` 加请求级同文本去重缓存（ContextVar，仿
  memory.take_query_vec 思路但跨模块）；② `retrieve()` 中记忆与知识两路
  `asyncio.gather` 并发（仅共享 search_query，无数据依赖），healer 与注入段保持其后。
- **收益**：主人轮 P50 检索延迟预计省 30-50%。**工作量**：小-中。**风险**：低
  （gather 用 return_exceptions 保留各自降级语义；trace.search_ms 口径改为两通道合计）。

## 2. 事件循环上的同步 SQLite：retrieve() 注入段约 19 个同步查询

> **✅ 已实施。**

- **问题**：上轮 to_thread 只覆盖 pipeline 层；`retrieve()` 的注入收集
  （profile/lessons/concerns/jargon/facts/goals/slang/mood 等，retrieval.py:458-490）
  仍同步跑在事件循环；`memory.search`/`knowledge._vector_search` 的 KNN/FTS SQL 也是
  async 函数体内联同步；`api/events.py:87-110` 批量落库同步。
- **方案**：a) 注入收集抽成纯同步函数 `_collect_injections(...)`，调用处一行
  `asyncio.to_thread`（与 pipeline 对 assemble 的处理同构；注入器无后台任务调度，
  不触发 prepare_turn 那种 loop 依赖）；b) memory/knowledge 的 SQL 段各拆 `_sync`
  私有函数进 to_thread（embedding 调用保持 await）；c) events 批量落库进 to_thread。
- **工作量**：中。**风险**：低-中（to_thread 内不得调 track_background；
  `_last_query_vec` 是 ContextVar，跨线程语义需验证）。

## 3. 数据访问：175 处裸 `connect()` + 手写 SQL，无 repository 收口

> **✅ 已实施（models/repo.py + api 层零 SQL；服务层存量按约定保留）。**

- **问题**：51 个文件直连直写 SQL（novel_entities 14 处、knowledge_domain 10 处…），
  `db_connection()` 上下文管理器仅 31 处使用；api/ 层也有 4 处直写 SQL
  （stats/reports/events/chat 的 /messages）。
- **方案**：渐进收口，不引 ORM。① 新增 `models/repo.py` 收口 5 类高频查询；
  ② api/ 层 4 个直连点全改走 repo（第一目标：api 层零 SQL）；③ 服务层存量保留，
  约定新增代码必须走 repo/db_connection。
- **工作量**：全套大；第 1-2 步约 2 天可独立交付。**风险**：低（纯等价重构；
  `_user_scope` 的 f-string 拼接习惯要封死在 repo 内）。
