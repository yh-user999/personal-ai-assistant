## 一、请求决策轨迹（request_traces）

### 为什么

现状检索链（域路由→路径选择→向量降级→自愈→注入）已是自动决策，但排障只能靠
分散日志复现。目标：**每轮对话的决策链可回放、可统计**。

### 设计

| 项 | 内容 |
|---|---|
| 存储 | 新表 `request_traces`，每轮对话 1 行 |
| 字段 | id、user_id、query、ts、routing(域路由结果 JSON)、retrieval_path(实体索引/混合/聚合提炼)、vector_degraded(0/1)、healer(触发词 JSON/空)、injection_bytes(各注入段字节数 JSON)、search_ms(检索耗时) |
| 写入 | chat 检索段结束后一次 INSERT，后台任务执行（不阻塞回复，失败仅记日志） |
| 保留 | 只留最近 30 天（定时清理，防膨胀） |
| 成本 | 每轮一次 SQL INSERT，零 LLM |
| 用途 | ①排障：`SELECT * FROM request_traces WHERE query LIKE '%炼神%'` 直接看决策链 ②评测：路由准确率统计的数据源 ③成本画像：与 60bc689 的 token 记账结合 |

### 验收

1. 任意一轮对话后，request_traces 出现对应行，字段完整
2. 超 30 天的行被定时清理
3. 写入失败不影响聊天回复（后台任务隔离）

## 二、意图分级的动态约束

### 为什么

同一份 system prompt 对所有意图一视同仁——枚举问题该强调"完整性报告"、
专名问题该强调"只答检索到的"、叙事问题该强调"注源"。现在只靠知识库注入的
内容引导，约束是缺失的。

### 设计

**意图标签零成本获取**——不新增 LLM 分类调用，从现有决策链的副产品里取：

| 信号 | 来源 | 标签 |
|---|---|---|
| 枚举句式命中 | `detect_enum_intent` | `enum` |
| 实体索引命中 | `build_entity_context` 非空 | `entity` |
| 分域路由结果 | `detect_domains` | `novel/manual/project/resume` |
| 自愈触发 | `index_healer.diagnose` | `healed` |

**约束注入**（system prompt 新增 `{intent_rules}` 段，按标签拼装）：

| 标签 | 注入约束 |
|---|---|
| enum | "清单类回答必须说明：确认 N 个、原文提到该有 M 个；不完整时明说'可能不全'" |
| entity | "只回答检索到的内容；禁止推测未出现的设定" |
| healed | "以聚合资料为准，标注'据原文梳理'" |
| novel | "可总结叙事，但关键设定必须注明章节" |
| 无标签 | 不注入（保持现状，零回归风险） |

### 验收

1. 枚举问题回答中出现完整性说明（"确认 3 个，原文提到 4 个"）
2. 普通闲聊问题无约束注入（prompt 与现状一致）
3. 现有 758 测试零回归

## 三、路由评测基准

### 为什么

域路由/枚举识别/自愈诊断都是正则+词表规则——改规则可能回退精度，目前没有
量化防线。

### 设计

| 项 | 内容 |
|---|---|
| 标注集 | `server/tests/fixtures/route_benchmark.json`：80-100 条（问题 → 期望域/期望路径/期望触发自愈），按真实对话采样 + 手工标注 |
| 评测器 | `server/tests/test_route_benchmark.py`：跑 detect_domains/detect_enum_intent/诊断，输出准确率/召回率，阈值断言（如路由准确率 ≥95%） |
| 运行 | 全量测试自动跑（规则改动即刻暴露回退）；也可离线输出混淆矩阵 |
| 数据源 | 现有对话回归集（60bc689）+ 真实提问记录 |

### 验收

1. 评测集跑通且当前基线达标
2. 规则被改坏时测试变红（负向验证一条）

## 四、后续总路线图（合并全部待办，按优先级排序）

### P0 近期（本次三件套，约 1 天）

1. 决策轨迹表 + 写入 + 清理 + 测试
2. 意图约束注入 + 测试
3. 路由评测基准 + 测试

### P1 检索自愈二期（方案已定稿，见《检索自愈与答案自检方案》）

后台自动实体抽取：预算闸（≤3 次/天）、幂等闸、置信闸、候选池 + 管理命令
（`查看候选抽取` / `确认抽取：X`）。

### P2 检索自愈三期

用户纠错反馈回路："不对，XX 不是境界" → 索引修正/候选池降级。

### P3 黑话模块（方案已定稿，见《黑话模块实施方案》）

一期（显式教学+追溯纠正+词命中注入+共享读）→ 二期（语境推断+转正状态机）
→ 三期（多义词打磨+淘汰策略）。

### P4 成本画像

token 记账（已有）× 决策轨迹 → 每轮/每意图成本报表，为注入瘦身提供数据。

### 排序原则

沿用既定评审次序：安全止血 → 当前体验 → 性能/成本 → 长期演进。
三件套是"体验与可观测"，自愈二三期是"演进"，黑话是"功能需求"，
成本画像是"性能"。无安全级事项。

### 评测基准首轮就抓到的两个真实缺陷

1. **候选词尾部残留**：`命图分为几种` 的候选被贪心正则吞成 `命图分为`，
   导致已覆盖词误触发自愈 → 修 `_FILLER_TAIL` 剥离完整枚举词
2. **"测试"一词误路由**：`_PROJECT_TERMS` 含"测试"太泛，闲聊"测试一下"
   被路由到项目文档域 → 从项目术语表移除

这正是评测基准的设计目的：规则改动有量化防线，缺陷当场暴露。

### 待办不变

P1 检索自愈二期 → P2 三期 → P3 黑话模块 → P4 成本画像。
