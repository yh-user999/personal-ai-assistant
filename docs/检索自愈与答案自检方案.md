# 检索自愈与答案自检方案（设计稿 · 待确认）

> 定位：让"小月"在检索没覆盖新概念时**自己发现、自己兜底、自己补索引**，
> 并建立"答案对不对"的分层判断机制。
> 版本：v0.1（方案评审稿，未实施）
> 立项依据：真实案例「炼神里面有哪些境界」——索引没覆盖境界体系，
> 判不出域被静默兜底，LLM 诚实地说"没有记载"，但书里其实有内容。

---

## 一、问题复现（实测数据）

| 现象 | 实测 |
|---|---|
| 域路由 | "炼神"不在实体索引/类名表/书名中 → 判不出域 |
| 判不出域的处理 | 静默走全域检索（**信号被吞掉**，没有上报"索引未覆盖"） |
| 全域检索 | 向量分数 0.04~0.06 无区分力；BM25 "炼神"全书仅命中 2 块叙事 |
| LLM 回答 | "资料里没有炼神内部细分的记载，我不编" |
| 真相 | 书里境界内容分散在 100+ 块叙事中；且书里写作"**练**神"（用户写"炼神"），错别字变体没做重搜 |

**核心教训**：小月"说不知道"这个行为本身是对的（诚实不幻觉），
失败的是三件事——①判不出域的信号被吞 ②核心词没命中时没有变体重搜
③说完不知道之后系统没有下一步动作。

## 二、判断框架：两层判断

### 1. 确定性判断（代码可验证，零 LLM）

| 检查 | 规则 | 失败时的含义 |
|---|---|---|
| 核心词命中检查 | 问题中的核心词（如"炼神"）必须出现在命中块里 | 没出现 = 这次检索就有问题，不是"书里没有" |
| 多块印证 | ≥2 个独立块支持同一结论 | 单块 = 孤证，降置信 |
| 枚举完整性 | "有哪些"类清单无法从碎片验证完整性 | 本身就是低置信信号，答案须标注"据原文梳理，可能不全" |

### 2. 概率性判断（LLM + 证据强度）

- 语义上片段是否真支持结论 → LLM 判断
- 最终裁判 = **证据链**：答案每句能否回溯到某章某块
  - 能回溯 → 高置信，可带出处
  - 不能 → 降级为"推断"或"不知道"

### 3. 原则：不知道是信号，不是失败

"判不出域 / 核心词未命中 / 相似度全线过低 / LLM 说没有记载"——
这四种信号都必须上报自愈流水线，而不是被兜底逻辑吞掉。

## 三、检索自愈流水线（自动补索引）

```text
用户提问
  ↓
① 域路由（硬编码词表 + 动态登记表双源）
  ↓ 判不出域 或 命中质量不足
② 检测器（index_healer.detect）——两个信号 AND 才触发：
   信号A：枚举句式（有哪些/哪几个/分为/分几/层次/等级/体系/境界）
   信号B：检索未覆盖（判不出域 / 核心词不在命中块 / 相似度全线过低）
  ↓ 触发
③ 本次兜底：枚举聚合检索
   候选词扩展（错别字/同音近形变体，每词≤3 个）→ FTS 捞 top 20 块
   → LLM 提炼 + 标注出处章节
  ↓ 同时后台（异步，不阻塞本次回复）
④ 类名自动登记进动态词表（幂等）
⑤ 自动实体抽取（复用现有 extract_entities，auto 模式）
   高置信 → 入库；低置信 → 候选池
  ↓
⑥ 下次同类问题 → 类名认识 + 专名在 → 高精度秒答
```

### 防误抽四道闸（自动化的对价）

| 闸 | 规则 |
|---|---|
| 句式闸 | 只有枚举句式触发；"炼神是谁"这类普通疑问不触发 |
| 预算闸 | 每天自动抽取 ≤3 次；同一类名当天只抽 1 次 |
| 幂等闸 | 已登记/已抽取的类名不重复 |
| 置信闸 | 抽取结果必须能定位到原文依据块；低置信只进候选池 |

### 候选池与人工确认（兜底安全网）

- 新命令：`查看候选抽取` / `确认抽取：X` / `废弃抽取：X`
- 用户说"不对，XX 不是境界" → 反馈修正回路（三期）

## 四、答案自检流程（回答前的分级）

```text
检索完成
  ↓ 核心词在命中块里吗？
  否 → 变体重搜（练神/炼神）→ 仍无 → 诚实说"没找到"+ 上报自愈
  ↓ 是
多块互相印证吗？
  多块 → 高置信直答（可带出处章节）
  单块 → 降级回答，标注"只在第X章看到，可能不全"
  零块 → 不答，走兜底聚合 + 自愈
```

## 五、落点与接缝（实施备忘）

| 改动 | 文件 |
|---|---|
| 动态类名表（建表+迁移） | `models/database.py` |

| 枚举聚合检索（变体扩展+top20 提炼） | `core/knowledge.py` 或 healer 内 |
| 核心词命中自检（回答前分级） | `api/chat.py` 检索后置 |

| 后台任务引用集（防 GC，同 fact_extract 模式） | `api/chat.py` |

## 六、分期

| 期 | 内容 | 效果 | 新增 LLM 成本 |
|---|---|---|---|
| 一期 | 动态类名登记 + 枚举聚合检索 + 核心词命中自检 | "炼神有哪些境界"本次就能答好 | 每次兜底 1 次提炼调用 |
| 二期 | 后台自动实体抽取（预算/幂等/置信闸 + 候选池） | 新体系自动入索引，不再人工跑 | 每次自动抽取 1 次调用，每天 ≤3 |
| 三期 | 反馈修正回路（用户纠错 → 索引修正） | 误抽可回收 | 零 |

## 七、验收用例（写进回归测试）

1. 判不出域 + 枚举句式 → 检测器触发，本次走聚合兜底
2. 核心词未命中 → 变体重搜命中（炼神→练神）→ 答案带出处
3. 普通疑问（"炼神是谁"）不触发检测器
4. 同一天第 4 个新体系 → 不触发自动抽取（预算闸）
5. 同一类名当天重复问 → 不重复抽取（幂等闸）
6. 低置信抽取结果只进候选池，不进正式索引
7. 动态类名登记后第二次同类问题 → 域路由直接判 novel 域
8. 现有 742 测试零回归

## 八、风险与应对

| 风险 | 应对 |
|---|---|
| LLM 成本被触发式提问刷爆 | 预算闸（3/天）+ 句式闸 + 幂等闸 |
| 误抽（把普通人名当体系抽） | 置信闸 + 候选池 + 用户确认命令 + 反馈回路 |
| 枚举答案不完整 | 标注"据原文梳理，可能不全"；设定卡是最终治本（另行方案） |
| 动态词表膨胀 | 登记时记录来源与时间，90 天未再命中自动退登 |

## 九、与现有方案的关系

- 与《黑话模块实施方案》互补不冲突：黑话模块管"词义"，本方案管"索引覆盖"
- 设定卡（novel_facts）仍是"有哪些"类问题的最终答案源；本方案是**检索层的通用兜底**，两者叠加
