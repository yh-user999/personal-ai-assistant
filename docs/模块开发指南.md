# 模块开发指南

本指南固化 2026-09 代码结构重组后的目录约定与新增模块流程，供后续接入新领域时直接照做。
路径均相对仓库根；服务端代码根为 `server/`。

## 1. 目录归属

**按领域建包**：一个领域一个包，放在 `server/app/<domain>/`。跨领域的通用能力才留在
`server/app/services/`（47 个模块，例如 `documents`、`reminders`、`sanitize`、`profile`）。

| 领域包 | 内容 | 入口 |
|---|---|---|
| `server/app/fitness/` | 健身事实记录、动作目录、训练计划、营养、AI 教练 | `service.py` + `api.py` |
| `server/app/group/` | 群聊短期上下文、心流、插话、注意力、关怀、表达、关系 | 见 `server/app/group/README.md` |
| `server/app/novel/` | 小说工作台：实体、词典、写作、章节分析、生成、审阅 | `service.py` 门面 + `api.py` |
| `server/app/chat/` | 聊天主链路（pipeline/retrieval/prompting/review/routing） | 跨层编排，不属任何单一领域 |

领域包内的分工：

- **纯函数/状态模块**（如 `app/group/context.py`、`heartflow.py`、`turn.py`）：直接 import 使用，不进注册表。
- **需要被注入 `ChatRuntime.services` 或允许 monkeypatch 的服务模块**：走注册流程（见 §3）。
- **只有群聊（`group_id` 非空）可达的模块**：包内 `README.md` 或 `__init__` 文档串必须写明当前可达性与无下游入口的事实，避免后人误判死代码。

基准/对比工具放 `server/benchmarks/`，不要留在 `app/`。

## 2. 四件套契约

### 2.1 `app/<domain>/service.py` —— 业务逻辑

- 纯函数优先；允许模块级缓存，但不要持有跨请求可变全局状态。
- 数据库访问：简单或跨领域访问走 `app/models/database.db_connection()` 或
  `app/models/repo.py`；一个领域存在多组相关查询、事务或联表结果时，新增
  `app/<domain>/repository.py` 作为该领域唯一 SQL 边界，服务层只做规范化和业务编排。
  API 层不再手写 SQL；服务层存量 SQL 允许保留，迁移完成的领域服务不得重新导入数据库模块。
- 需要 `user_id` 隔离的查询统一用 `app/core/memory._user_scope` 的既有模式，不自行拼 SQL 片段。

### 2.2 `app/<domain>/api.py` —— 路由

- 导出模块级 `router = APIRouter()`，由 `app/main.py` 以 `prefix="/api"` 挂载；
  领域内路径自带域名段（如 `/fitness/...`、`/novel/...`），**URL 前缀一旦发布不随目录迁移改变**。
- 错误响应：新端点统一用 `app/api/errors.api_error(status_code, code, message)` 构造
  `detail={"code", "message"}`；存量裸字符串 detail 端点逐步迁移。
- 表单/请求体用 Pydantic 模型，字段一律带 `max_length`/`ge`/`le` 等约束（对齐既有 `fitness/api.py` 风格）。
- 同步 SQLite 调用在 async 端点中用 `asyncio.to_thread` 移出事件循环。

### 2.3 `app/models/database.py` —— 建表与迁移

- **新表**：写入基础 schema 脚本（`CREATE TABLE IF NOT EXISTS`，当前 56 张表），并把表名补进
  `app/main.py` `_database_check()` 的 `required` 集合（`/api/ready` 会核对新表是否存在）。
- **新列**：不修改既有建表语句，只往 `_MIGRATIONS` 列表追加一条
  `ALTER TABLE ... ADD COLUMN ...`；`init_db()` 会容忍 `duplicate column name`，保证幂等。
- 每次结构变化 `SCHEMA_VERSION` +1（当前 17）。迁移顺序有依赖时必须在 `init_db()` 中显式排序并注释原因
  （参考 `_migrate_user_id` 必须先于 `asked_at` 加列的既有注释）。
- 数据回填与迁移同事务提交；失败不得留下半个迁移列。

### 2.4 `app/chat/routing.py` —— 聊天触发词（可选）

- 领域模块如需零 LLM 快捷命令：实现 `async def _<domain>(ctx, runtime)`，用
  `_make_handler()` 包装后登记进 `_COMMAND_HANDLERS`（按注册顺序短路）。
- 同时决定两件事：`GUEST_BLOCKED_HANDLERS`（访客是否可用）与群聊作用域限制
  （当前群内只放行 `identity`/`time`，其余命令自动跳过）。
- 不需要聊天触发的模块（如纯 API 领域）跳过本节。

### 2.5 `server/tests/test_<domain>*.py` —— 测试

- 每个领域包配套 `tests/test_<domain>*.py`，覆盖主路径 + 边界；
  跨模块行为测试放 `tests/test_<domain>_<topic>.py`（参考 `test_fitness_api.py`、`test_novel_runner.py`）。
- 服务模块经 `ChatRuntime.services` 注入，测试用 `services_registry.make_services(overrides)` 构造替身；
  不要直接依赖真实 DB。

## 3. 注册流程（新增领域模块照做）

1. **建包**：`server/app/<domain>/__init__.py` 写一句领域职责文档串。
2. **实现四件套**：`service.py`（§2.1）、`api.py`（§2.2）、必需的建表/迁移（§2.3）。
3. **注册服务**（若模块要进 `runtime.services`）：在 `server/app/chat/services_registry.py` 两处登记——
   `SERVICE_MODULES` 加一行名字；若模块属独立领域包，再在 `DOMAIN_MODULE_PATHS` 写完整路径
   （否则默认 `app.services.<name>`）。
4. **挂路由**：`server/app/main.py` 中 `include_router(...)`，并在 `ROLE_RULES` 显式登记
   该前缀允许的角色集合——不要依赖"未登记即全角色可用"的静默放开。
5. **聊天触发**（可选）：按 §2.4 登记命令与访客/群聊限制。
6. **测试与验证**：

   ```bash
   cd server
   .venv/bin/ruff check app tests
   .venv/bin/python -m pytest tests/ -q
   .venv/bin/python -c "import app.main"     # 冒烟：路由装配无 ImportError
   ```

7. **文档**：更新本指南 §5 的清单状态；涉及运行事实的改动同步 `AGENTS.md`。

## 4. 重组后的现状（2026-09）

- `server/app/chat/pipeline.py` 只保留一轮聊天的编排骨架；群聊前置编排、计划字段写入、
  提示注入与收尾记账已迁到 `server/app/group/turn.py`（`prepare_group_scene` /
  `apply_group_plan_fields` / `record_group_social_trace` / `apply_group_prompt_injections` /
  `finalize_group_turn`）。
- 健身结构化数据（`catalog`、`nutrition`、`training`）已由
  `server/app/fitness/repository.py` 收口 SQL；旧 `fitness/service.py` 的自由文本台账与
  知识卡仍是兼容链路，尚未纳入本次迁移。
- 群聊服务模块通过注册表按名注入（`group_care`、`group_expression`、`group_relationship`）；
  上下文、心流、插话、注意力、`turn` 为直接 import 的纯函数/状态模块。
- 迁移后的 import 全部指向新领域包；`app/services/` 不再存有 fitness/novel/group 专属模块。
